# 第一部分 项目背景与整体设计

## 0.1 目标与约束

**目标**：做一个“自进化、自动演化、会主动交互”的电脑操作智能体。本地小模型执行任务；知道自己不会就主动求教（云端老师或用户演示）；把学到的东西变成经过验证的技能/记忆；空闲时自己练习、修复和整理能力；并主动向用户汇报和确认（`roadmap.md` §1、`docs/plans/self-evolving-proactive-agent-2026-10-14.md`）。

**约束（这些约束决定了很多设计）**
- **学生模型**：Agents-A1-4B（Q4_K_M 量化，llama.cpp 运行），能在个人电脑上跑。选型过程见 `evidence/2026-10-14-student-screening.tar.gz`。
- **老师**：DeepSeek（`deepseek-flash`），按调用付费。**总预算 $4**（用户 10-14 批 $1，10-15 追加 $1，10-16 追加 $2），所有老师调用必须走同一本全局账本。
- **算力**：本机跑模型会让 Mac 卡死（10-14 实际发生），所以从 E-1 起所有实验在 **Kaggle 免费 T4 GPU** 上跑；本机只在用户同意时做应用的端到端验证。
- **隐私**：用户的真实使用数据只存本机；脱敏后才能用于训练。

**为什么这些约束有研究价值**：大厂的自改进工作用 27B 以上模型和大量算力。“4B 模型 + 几美元 + 免费 GPU”下什么方法还成立、什么不成立，本身就是一个有价值的问题——也是我们和同期工作的区别（第 20 条）。

## 0.2 架构：四个环 + 交互层

```
交互层（主动）：求教卡片 / 学习汇报 / 启用确认 / 👍👎（heartbeat 通知队列 + 头像窗口卡片）
① 执行环（秒）：观察 → 行动 → 自检 → 求教门（能力自评决定是否先问）
② 学习环（每任务）：失败/求教 → 老师示范 → 提取技能 / 存轨迹记忆 / 写经验规则 → 验证 → 入库
③ 演化环（空闲/后台）：选薄弱族 → 生成变体自练 → 修复/合并/停用技能 → L2 策略演化（架构师）
④ 巩固环（10-18 新增）：带指导重做新变体 → 只留验证通过 → 删掉指导 → LoRA → 不带指导验收 → 启用/回退
```

四层适应机制（README）：L0 情景记忆（轨迹）→ L1 程序性记忆（技能）→ L2 脚手架演化（策略代码）→ L3 巩固（权重）。

关键模块：`core/evolution/stream.py`（学习流与各实验臂）、`competence.py`（能力自评）、`relevance.py`（相关性门控与自动归族）、`skills.py`（技能库）、`architect.py`/`l2_selection.py`（L2）、`practice.py`（自练与维护）、`teacher_budget.py`（账本）、`lessons.py`/`leakage.py`（规则与泄漏筛查）、`core/trajectories.py`（真实使用轨迹）。

## 0.3 基准与评测纪律

**Kage-Stream v1（文件任务）**：6 个按种子程序生成的任务族——F1 子集选择、F2 区间合并、F3 日志聚合、F4 CSV 变换进入学习流；F5 文本规范化、F6 配置迁移**只用于评测**（测迁移）；另有 3 类只读负例（`read_preserve`、`inspect_question`、`lookalike_readonly`，测“会不会乱改”）。每个实例由（族，种子）完全决定；隐藏用例由参考实现算出，不出现在学生/老师能看到的内容里（`public_view`）。

**Kage-Stream-Web（浏览器任务，C1）**：表单、发票总额、通知设置、酒店筛选 + 只读负例（见第 14 条）。

**纪律**
- **种子分区**：stream 1000–4999 / calibration 5000–8999 / eval 9000–12999 / practice 13000–16999 / validation 17000–18999，`split_of(seed)` 推导，代码里不能混用。
- **难度标定**：每个能力族的原学生成功率要落在 10–50%（太简单没有学习空间，太难学不会）。
- **冻结**：流与评测清单冻结并记录 sha256（`eval/stream_v1/`、`eval/stream_web_v1/`），之后只能出 v2，不能改。
- **检查点**：评测时关闭学习和求教（冻结库、不更新能力自评），只评学生自己。
- **对照臂**：A0 原学生；A1 同样预算拿来重试；A3 轨迹记忆；A4 技能库；之后的 A4g/A4m/A4mG/A5/A6 等见各条。
- **统计**：Wilson 置信区间；配对 McNemar 精确检验（同一道题在两臂上的对错）；原学生多次重复给出波动范围（第 7 条）。

# 第二部分 发现与教训

## 1. 恢复钩子的接口缺陷让 G2 基线“必然误用”

**背景**：项目在 10-14 之前由另一个模型（Codex）推进，做过 G1（让系统学会“恢复”：失败后生成恢复策略并晋级）和 G2（检验学到的策略会不会误用）。G2 基线里，一个读取类的只读任务被 G1 晋级的策略“修坏”了。

**发现过程**：10-14 重新审查时读了 `core/agentic_loop.py`，发现恢复钩子在“执行过工具后模型不再调用工具”时触发——也就是**每次正常结束都会调用恢复策略**。再看 G1 晋级的策略源码，写死了 `skill_id == "repair_knapsack_selection"`，读到任意文件就派发技能，不看任务目标。

**根因**：不是“学到的策略坏”，而是**接口让策略无法区分“正常结束”和“失败后结束”**——它拿不到触发原因、最终回复、写过哪些文件。在这种接口下，任何策略都很难不误用。

**解决**：给钩子加上下文（触发原因 `finish_attempt`/`finish_after_tool_error`、最终文本、写过的文件、最近工具是否成功），并新增 `request_help` 动作（直接以“求教”结束，不执行任何动作），供求教门接老师或用户（`core/agentic_loop.py` 的 `recovery_context`，测试 `tests/test_recovery_context.py`）。历史 G1/G2 策略的输入保持不变，可复现。

**教训**：**实验结论可能是接口的必然结果，而不是方法的性质。**先读代码确认“它能不能做对”，再解释“它为什么做错”。G2 的误用作为负发现保留，但不再沿那个方向投入。

## 2. 300 token 截断制造了“原学生≈0%”的假象

**背景**：E-0 第一次跑原学生 A0，成功率接近 0。

**发现过程**：查模型轨迹，学生每一轮工具回复都在 300 token 处被截断（`finish_reason=length`），`write_file` 的内容永远发不完整。

**根因**：`AgenticLoop` 的工具轮硬编码 `max_tokens=300`——这是“陪伴聊天产品”的设定（回复要短），被实验路径继承了。实验脚本里给学生设的输出上限只对另一种模式生效，对学生无效。

**为什么严重**：技能臂只需要发一个很短的 `skill_call`，不受截断影响——于是**“技能库大幅领先原学生”会是截断造成的假结论**，是一个混杂因素。

**解决**：把上限变成类属性（产品默认仍 300），实验链对所有臂统一用 1024（= 服务端 `-n`），写进冻结配置；两次作废的运行保留为 `A0-void-300tok`，不计入结果（工作日志 W5-1 准备）。修复后 A0 前 4 题 1/4 通过，无截断。

**同时做的检查**：产品里的其他启发式（天气、命令推断、自动保存）会不会在实验里触发？对 E-0 全部 32 条指令跑了路由分类与命令推断：0 命中，所以不需要额外开关（`docs/code-map.md`）。

**教训**：**基线太差时先怀疑基础设施。**“我的方法赢了”之前，先确认对照组没有被系统缺陷压低。

## 3. 技能检索要求“每个词都匹配”，调用率只有 15%

**背景**：E-0 里 A4（技能库）学到了技能，但学生几乎不用。

**数据**（工作日志 W2-5）：技能库非空时的 54 次能力题里，46 次“有预览但没调用”，其中 45 次是 `skill_search` 返回空列表后学生自己手写；成功调用仅 8 次（调用率 15%）。

**根因**：`SkillCatalog.search` 要求查询里的**每个词**都出现在技能 id 和描述里，学生用自然语言搜索几乎必然落空；学生又更相信搜索结果而不是预览。另一个原因：老师提取的技能太窄（日志技能只支持按 service 计数，而这族还有按 level 计数的变体）。

**解决**：检索改为按共有词数排序（id 按下划线拆词、复数归一、≥3 字母、零重叠不返回）；提取提示要求把族内变化做成参数、描述以“Use this when”开头、代码 <60 行。离线回放 E-0 全部真实查询：能力查询命中 0 → 143/144；负例查询命中 8–10/37（误用风险上升，所以复跑时重点看负例）。

**结果**：复跑 A4-w25 技能调用率 75%（6/8、6/8），负例 4/4、误用 0——满足里程碑 M1（学生在有技能时真实调用）。

**教训**：**“学到了”和“用上了”是两件事**，必须分别测。这条也是第 15 条（不照做）的早期伏笔：小模型对工具/指导的使用方式比想象中脆弱。

## 4. 教师回复 23/25 次只是缺一个右括号

**现象**：技能提案经常 JSON 解析失败，触发付费的“格式修复”请求；修复请求要带回上一条回复，体积翻倍，3 次撞上 12000 字节的单次输入上限而中止。

**数据**：E-0 全部技能提案中 25 次 JSON 解析失败，**23 次只是缺最后一个 `}`**，`finish_reason=stop`（不是被截断）。

**解决**：`mutator.parse_proposal` 先严格解析，失败时只尝试补一个 `}`，补完必须是对象才接受，并记录 `json_closed: true`；其他损坏仍走原修复流程。单次输入上限从 12000 放宽到 24000 字节（约 6k token、满额约 $0.002/次），经用户同意写入预算规则。

**教训**：**统计失败的具体形态再修**，往往有一个便宜的针对性修法；省下的是钱，也避免了次生问题（撞上限）。

## 5. 从示范学习非常有效，但技能库并不比轨迹记忆强

**背景假设（H1）**：从老师示范学习能提升学生；而且把示范提炼成“参数化技能”应该比直接存“原始轨迹”更好（技能更结构化、可复用、可迁移）。

**E-1 结果**（Kaggle v5–v7，2 种子，流 60 题，48 道同类评测题；`evidence/reports/e1-report`，口径按第 7 条更正后）：

| 臂 | cp0 | cp30 | cp60 |
|---|---|---|---|
| A0 原学生 | 14/48（29%） | — | — |
| A1 同预算重试 | 12/48（25%） | — | — |
| A3 轨迹记忆 | 14 | 38 | 42/48（88%） |
| A4 技能库 | 14 | 34 | 39/48（81%） |

配对（cp60，同类题）：A4 vs A0 25:0，p=6e-8；A4 vs A1 27:0；**A4 vs A3 5:8，p=0.58**。旧的背包问题能力从 0/12 恢复到 11/12（A4）。未学族（F5/F6）没有提升。负例 24/24、零误用。

**结论**：从示范学习的效果非常大；但**技能库不比轨迹记忆强**。按任务书的停止规则（M3），停止扩展、先诊断。

**诊断（离线分析，未调用模型）**：A4 cp60 的 48 题里，31 题调用技能通过、8 题手写通过、8 题失败且没调用技能、1 题技能输出错误。失败几乎全在日志族。
- **根因 1：技能预览按 id 字母序取前 3 个**，与任务无关；库长大后（种子 1 有 10 个技能）相关技能被挤出预览。相关技能在预览里时 17/18 通过，不在时 22/30，8 次失败全在后一组。而 A3 的示范是按指令相似度检索的——比较对 A4 不公平。
- **根因 2：步数**：学生即使搜到正确技能，也会反复搜索/读文件，把 5 步用完。

**修复与后续实验**（都标为“看过结果后的事后改进”）：
- E-1b（v8）A4r：预览按相关性排序。38/48，仍不优于 A3（A4r vs A3 6:10，p=0.45）。剩余失败：4 次技能太窄，6 次预览里有相关技能但学生没调用。
- E-1c（v9）A4g：技能入库前还要在流里最近 2 道同族题上通过并真实调用，不通过就把失败题的公开指令反馈给老师改写一次；A4m = A4g + 轨迹记忆。A4g 40/48、A4m 43/48；**技能调用率显著上升**（A4g 45/48，E-1 的 A4 约 32/48），**但通过率没跟着升**——调用多了，部分技能仍不对。学习臂之间两两都不显著（A4m vs A3 6:5，p=1）。

**教训**
- **结构化不一定赢。**技能听起来比原始轨迹高级，但在这个规模上没赢。
- **工程细节能决定一个方法的成败**：一个字母序的预览就让技能库失效了一大半。
- **诚实标注“事后改进”**：看过结果再修的方法不能替代原结论，只能作为探索。

## 6. 学到的东西会干扰陌生任务：相关性门控

**发现过程**：E-1c 里注意到，**所有学习臂在未学族（F5/F6）上的 cp60 都低于起点 16/24**（A4 14、A3 12、A4r 9、A4m 9、A4g 6），而且这些题上没有任何技能调用。

**两种解释**：①学到的技能/示范被塞进了不相关题目的提示里，干扰了学生；②A0 的起点（只测过一次）本身偏高。当时无法区分，两种都要验证。

**根因（干扰部分）**：`preview_relevant` 在词重叠很弱时仍给出 3 个技能；A3 的记忆用 Jaccard ≥0.2 判断相关，太松。离线标定发现：**词集合 Jaccard 两两分不开族**（同族换说法低至 0.18，跨族高至 0.29）。

**解决（P3，`core/evolution/relevance.py`）**
- 相关性改用 **TF-IDF 余弦**，文档频率**只来自智能体自己已经见过的指令**（不用任何基准标签），阈值 0.3。按真实流顺序回放：评测题对同族已验证指令 ≥0.38、对其他能力族 ≤0.25；到达时 0 漏 0 误。
- **门控**：技能只在接近其已验证指令时可见，示范同理；**门控全空时，学生的整个请求与原学生逐字节相同**（集成测试证明）。
- **自动归族**：智能体自己按相似度把任务聚类，用来记能力和求教，不再用基准的族标签。两种子共 21 个聚类对 14 个（族×种子），纯度 100%，同族不同说法有时会拆开。

**结果**（E-2 v10 + E-2b v11）：门控臂在 48 道未学族评测题上**一次都没注入技能或示范**，没有技能调用；未学族分数约 6/12，落在原学生同环境重复的 5–8/12 区间内；无门控的 A4m 为 4.5/12，低于区间。负例 24/24、零误用（无门控的 A4m 曾有 1 次误用）。同类题上门控从未挡掉该给的技能。

**最终解释**：E-1c 的“学后低于起点”**一半是干扰（已被门控消除），一半是 A0 单次评测偏高**（第 7 条）。

**局限**：TF-IDF 只适合模板化的基准指令；真实自由文本需要嵌入模型（报告中注明）。应用里的中文请求另外加了二字组分词（第 13 条）。

**教训**：**记忆不是越多越好。**“不相关就什么都不给，和没学过时完全一样”应该是硬约束，而且要用“请求逐字节相同”这种可检验的方式测试。

## 7. 先量波动，再谈效果：GPU 非确定性与统计口径

**现象**：E-2 里同一个请求多次运行，结果不同。

**我犯的错**：当时在日志里写“学生用温度 0.7 采样”，并据此解释波动。后来查代码发现 `RecordedLocalProvider` **强制温度 0**，服务也是单槽——这个解释是错的。已在技术报告和工作日志里更正（第 21 条）。

**真实原因**：llama.cpp 在 GPU 上的计算**不是逐位可复现的**（并行规约时浮点运算顺序不同），温度 0 的贪心解码也会在某些 token 上走不同的分支。

**数据**（E-2b，技术报告 §5.4）：同环境 A0 重复（加第 6 版共 4 次），48 题里 **15 题结果变化**，全部不是超时；同类题 7、10、13、7/24；未学族 8、5、8、6/12。

**影响**：此前把 A0 只评测一次、当作常量，**配对 p 值偏乐观**，也造成了“学后低于起点”的部分错觉。

**同时发现的统计口径问题**（报告口径更正，10-16）
- 不学习的臂（A0/A1）的“同类题”被算成全部 6 个能力族（A0 30/72），与学习臂的 4 族不可比 → 改为只算学习臂学过的族（A0 14/48）。
- McNemar 配对实际用了全部评测题（含未学族与负例），而文字写的是“同类题” → 改为同类题为主、全部题另列；p 值不再四舍五入。
- 新增 `scripts/experiments/rebuild_reports.py` 从证据包重建全部报告。

**解决（之后的规矩）**：原学生每个实验跑 ≥3 次给出波动范围；配对只在同类题上做；把“学习 vs 不学习”（差距约 45 个百分点，远超波动）和“学习方法之间”（差距小于波动）分开下结论；浏览器实验 C2/C3 都包含 A0 同环境重复。

**教训**：**温度 0 不等于确定性。**比较方法之前先测系统本身的噪声；很多“提升”在噪声面前不成立。

## 8. 主动求教：从“几乎每题都问”到“几乎从不问”

**背景假设（H2）**：智能体应该“知道自己不会”，在尝试之前主动求教，这样比失败后再求教更省（省掉学生的失败尝试）。

**第一版（E-0 的 A5，按能力自评求教）**：观测少于 2 次先自己试；之后若期望损失 `(1-p)×value > help_cost` 就先问。结果：**探索 2 次后几乎每题都问**（14 次事前求教，学生在流内只自己尝试了 6 题），“精准率”100%（近似定义）。问得准，但问得太多，学生几乎没机会自己做。

**第二版（E-2 的 A5，proactive_gated）**：只有“能力低 **且** 没有任何相关知识 **且** 之前在这个聚类上求教有用”时才先问。结果：**120 个流任务里只触发 1 次**（精准 1/1）。

**原因**：在一个新聚类上第一次失败后，“失败后求教”就已经教会了相关的东西；之后策略改为先自己试，“能力低且一无所知”的状态很少持续两次以上。

**结论**：H2 在这个基准上**没有被检验**，而不是被证伪——机制几乎没有发挥空间。

**教训**
- 求教策略在“问太多”和“从不问”之间很敏感，需要按成本校准，而不是凭直觉设规则。
- **“未被检验”和“被证伪”要分开说**，这是诚实报告的一部分。
- 可能的改进（未做）：新聚类用全局先验直接事前求教，省掉第一次失败尝试。

## 9. L2 架构师：先是一次都没提案，后来把噪声当改进

**背景**：L2 = 让云端“架构师”（参考 Meta-Harness 的思路）改写智能体自己的策略代码。可演化的对象只有 4 个（提示模板、技能选用、求教策略、恢复），各有固定函数签名；评分器、预算、内核不在可改范围内。架构师只能只读地浏览档案（隐藏评分已删除）；候选代码经过 AST 检查（禁止 open/exec/网络等）；**晋级规则**：父子策略在同一批验证题上跑，无退步且至少一题变好才晋级（`core/evolution/architect.py`、`l2_selection.py`）。

**第一次（E-2，v10）**：架构师 **6 次全部 `turn_limit`**——8 轮都在读档案文件，一次提案都没给（每次约 $0.003–0.004）。L2 实际没被检验，A6 与 A6-fixed 等价。
- 原因：它不知道自己只有 8 轮。
- 修复：系统提示写明总轮数；每次工具结果后告知剩余轮数，最后 2 轮必须给出结果；验证概览（每题得分、显示的技能、最高相似度）直接写进说明，少读文件。

**第二次（E-2b，v11）**：6/6 给出提案（每次 $0.004–0.006），**2 次晋级**，都是因为“约 10 道验证题里 1 题变好、无退步”。
- 种子 1 晋级的策略把相似度阈值从 0.3 降到 0.1——**等于撤掉了相关性门控的保护**，会放进弱相关技能。
- 种子 2 晋级的是一段基于正则的规则。

**结果**：A6（有架构师）同类题 41/48、未学族 9/24；A6-fixed（固定规则）45/48、12/24。A6 vs A6-fixed 同类题 1:5，p=0.22。**L2 没有帮助，而且有变差迹象。**

**根因**：学生本身的随机性（第 7 条：48 题里 15 题会翻转）远大于“10 题里 1 题变好”这个信号。单次运行、小验证集的晋级规则会选中噪声。

**改进方向**（未做，列入路线图待办，排在巩固环之后）
- 晋级必须在重复运行上稳定改进（例如每题 3 次多数），验证集要包含未学族样例。
- 借鉴谷歌 Harness²（第 20 条）：在同样条件下**成对试跑**候选与现行策略，按行为证据组合改动，而不是看一次分数。

**教训**：**自我修改最大的风险不是改不出东西，而是评估太弱时会自信地选中噪声。**还有一个工程层面的教训：给智能体的预算（轮数）必须显式告诉它，否则它会把预算全花在“看”上。

## 10. 后台自练与技能维护：做了，但没有显著收益

**设计**（`core/evolution/practice.py`）
- **自练**：按能力自评选“成功率接近 50%”的族（学习前沿），从 practice 种子区间取新题，只用本地学生（类里根本没有老师参数），失败写入修复队列。
- **维护**：同一技能失败 ≥2 次时让老师提一次新版本，必须在这些失败题 + 该技能最近 2 个成功题上全部通过才替换；技能停用（≥3 次调用成功率 <34% 或 30 个任务没用）；描述相似的技能只记录合并候选。
- A6 每 10 个流任务做一轮（6 道自练 + 维护）。

**结果**（E-2）：A6/A6-fixed 各 12 轮；自练 62/72 vs 56/72 通过；修复接受 1/2 vs 0/3；停用 2 vs 2。A6-fixed 同类题 45/48 是各臂最高，但 vs A5 6:4，p=0.75，不显著。

**教训**：在这个基准上，学习流本身已经把同类题推到 80–90%，自练和维护的增量被波动淹没。要证明它们有用，需要更难、更长的任务分布或更多重复。

## 11. 教师预算与账本设计

**问题**：老师按调用付费，总额很小；多个实验并行、会中断续跑、还有后台调度器和应用里的真实使用都会调用老师，必须保证总额不被突破。

**设计**（`core/evolution/teacher_budget.py`）
- **唯一全局账本**（SQLite，`~/.config/kage/teachers/ledger.sqlite`），所有老师调用都必须走它；上限写在代码常量里（现在 $4）。
- **先预留后结算**：调用前按最坏情况（输入估计 + 输出上限）预留，结束后按实际用量结算；进程中断时按上限保守结算——所以换实验目录也重置不了总额。
- **单价保守**：按 DeepSeek 的非缓存价格（$0.30/$1.20 每百万 token）计，实际账单只会更低。
- **实验级上限**：每个实验有自己的花费上限，并比账本上限低 $0.10 的余量，保证“实验先停”而不是“账本拒绝”（拒绝的结果曾被错误缓存，见第 12 条）。
- **Kaggle 端独立账本**，跑完把实际花费用 `charge_external` 记回本机账本（例：C2 $0.2451，本机 $2.6739 → $2.4288）。
- **应用里的真实使用**：每日上限 $0.05（`LedgeredTeacher`），超出改为请用户演示。
- **教师缓存**：老师从干净初始状态解每道题，按 task_id 缓存，跨臂、跨种子共享——**云费不随实验臂数量增加**，这是 $4 能做这么多实验的关键。

**花费记录**：截至 10-20 老师总共约 $1.57（E-0 约 $0.095；E-1 累计 $0.515；E-1c $0.10；E-2 $0.231；E-2b $0.073；示范补收 $0.205；C2 $0.245；应用真实使用 $0.003 等，详见工作日志）。

**教训**：**预算控制要做成机制，而不是靠自觉**：先预留、全局唯一、中断保守、跨实验共享缓存。

## 12. Kaggle 免费 GPU 上的实验基础设施

完整踩坑记录见 `docs/development/kaggle-runbook.md`（13 条）。最有代表性、也最有“教训价值”的：

1. **构建镜像没有 libcuda**（连 stub 都没有），llama.cpp CUDA 编译失败 → `GGML_CUDA_NO_VMM=ON`（只影响显存池分配方式，不改计算）。
2. **命令行推送的运行读不到 Kaggle Secrets** → 正式运行一律从网页 Save & Run All 启动；阶段由仓库里的 `scripts/experiments/kaggle_phase` 文件控制（改阶段 = 推送一次，不用改笔记本）。
3. **第 5 版大部分作废**：
   - 6 台并行服务里 3 台无报错中断，之后的题 `Connection refused`，runner 标了 `crashed`，**但学习流把它当成学生失败计分**（A0 负例 0/24、A3 cp60 0/48）。→ `InfrastructureError`：崩溃不是能力结果，直接抛出、不记录，由总控重启并按题续跑。
   - Kaggle 账本上限太低，教师缓存 109 条里 60 条是 `budget_exhausted`，**也被当成示范缓存**。→ `TeacherBudgetExhausted`：预算拒绝时停止学习、检查点照跑、绝不缓存。
4. **重启后 20 秒内又“崩溃”**：重启复用同一个 run_id，runner 直接返回缓存的崩溃结果，从未调用模型 → 按尝试次数加后缀 `KAGE_RUN_SUFFIX=-aN`。
5. **内存泄漏**：v9 内存 5.9→31.7GB（共 32GB），任务被杀。根因是这一版 llama-server 默认 `--cache-ram 8192`（每台最多 8GiB 主机内存缓存旧提示），4 台就占满 → `--cache-ram 0`（不改模型计算与输出）。修复后 v10 峰值 4.8GB。本机 Mac 卡顿大概率也是同一原因。
6. **预编译复用**：每次全新虚拟机编译 llama.cpp 约 27 分钟 → 把编译结果存进输出，下次作为输入复用（准备阶段约 40 秒）；**复用时也要再存一份**，否则下一版又找不到（v7 因此重编了 27 分钟）。
7. **取消的版本没有输出**：取消 v12 后，下次运行找不到预编译程序和教师缓存 → 启动前确认输入挂的是最后一个成功版本。
8. **排队**（10-18）：T4×2 排队 2 小时没开始；这个笔记本只提供 T4×2/TPU，没有 P100 可选 → 取消重提后立即开始。
9. **CLI 下载输出会逐个拉取几千个文件**（很慢）→ 只等压缩包到达，然后自己解包。

**教训**：**“崩溃”和“失败”必须严格区分**——基础设施问题一旦被计成能力结果，整组数据都不可信。所有长任务都要可续跑、幂等、不重放已付费的调用。

- **R3 流水线连续三次在训练前失败（v22–v24，10-21）**：huggingface_hub 进程内升级导致新旧模块混用；transformers 5 只加载文本部分、层名少了 `language_model` 前缀导致 LoRA 一个层都没挂上；Kaggle 预装旧 torchao 让新 peft 直接报错。另有两处是本地提前发现的：llama.cpp 的 LoRA 转换器无法处理 Qwen3.5 线性注意力的 `out_proj`（V 头 32 ≠ K 头 16，需要重排列），以及 6144 上限静默丢掉了三分之一的 web_catalog 样本。**教训**：冒烟测试必须和正式运行走同一条路径（同样的目标层、同样的验证、最长的样本），且能在本地验证的部分（转换器用随机假适配器、损失函数用小随机模型、peft 包装用小模块）都先在本地验证——每次 Kaggle 往返约 20 分钟，几小时的正式训练失败代价更大。**面试讲法**：讲“把失败前移”：每次失败都补一个更早的检查，而不是只修那一个错。

## 13. 应用闭环：在日常使用中学习，以及隐私设计

**为什么做（10-16 计划核对）**：E-1/E-2 之后发现与目标有三个差距：①闭环只在基准里跑，Kage 应用本身没接上；②学到的东西不跨族迁移；③任务都是“改文件”的编程题。用户定顺序 **A（接应用）→ C（浏览器）→ B（蒸馏）**，理由是先让真实使用和浏览器任务产生更多、更多样的数据，再做训练。

**实现（A1–A4）**
- **A1 消息卡片**：后端早已能推送求教/汇报/确认消息，只缺前端——头像窗口新增卡片（好/稍后/不再提醒），回复写回后端（`kage-avatar/src/notices.ts`）。
- **A2 轨迹库**（`core/trajectories.py`）：主循环的每次模型调用被包装记录，每个真实任务按“学生格式”（请求 + 工具 → 回复）存到本机 `~/.kage/trajectories/`，可查看、删除、关闭；任务结束推送 👍/👎；证据分级：用户确认 > 自动检查（读回校验）> 未被纠正，只有前两类可进训练集；约 1/10 按 id 哈希留作真实场景评测；`export_redacted` 只导出训练集里有成功证据的任务并脱敏（令牌、凭据、邮箱、电话、IP、用户目录、人名）。
- **A3 老师重做**：👎 后推送求教卡片（`Heartbeat.reply_now`：对用户刚做的动作的直接回应，不因“用户活跃”被延后，但仍受静音/免打扰限制）；用户接受后 `LedgeredTeacher` 在隔离的执行环里重做，记为 `source=teacher` 的轨迹。
- **A3b 经验复用**（`core/evolution/real_memory.py`）：👍 的任务和自动检查通过的老师重做作为“经验”；新请求用 TF-IDF 检索，相似度 ≥0.45 才附上（比基准的 0.3 更严，因为真实请求是自由文本、错误提示代价更大），并提示“参数按这次的要求来，不要照抄”。
- **A4 空闲自练**（`core/evolution/real_practice.py`）：从真实文件任务里选种子（失败的优先）→ 老师出同类变体并附一个只读的 `check(ws)` 检查函数（AST 校验禁止写/删/执行/联网）→ 学生在临时目录里、只用文件工具做 → 子进程跑检查 → 存 `source=practice` 轨迹 → 发学习汇报。默认关闭，用户在 10-16 打开。

**本机端到端验证（用户同意本机起模型）**：真实任务“在 work 目录建 hello.txt”→ 学生完成 → 👎 → 求教卡片 → 接受 → 老师重做（$0.0026）→ 👍；相似新任务“建 greeting.txt”命中老师重做经验（相似度 0.87），学生按新要求做对；空闲后自动一轮练习，老师出“建 notes.md”变体，学生做对、检查通过、汇报送达。

**踩坑与修复**
- **划分泄漏**：老师重做的轨迹原来按自己的 id 划分训练/留出，会把**留出任务的做法带进训练集** → 改为继承原任务的划分（加测试）。
- **中文请求没有分词**：相似度只认英文单词，中文请求几乎比不出相似度 → `relevance.tokens` 加中文二字组（基准全英文，不受影响）。
- **端口冲突**：用户 Mac 上 OrbStack 占用 8080，Kage 的本地模型起不来 → 默认端口统一改为 18080（一个常量贯穿运行时、代理、路由）。
- **求教卡片被延后**：👎 之后的求教卡片因“用户正在活跃”被心跳策略压住 → 新增 `reply_now`。

**教训**：**真实使用的数据管道，隐私和划分要在第一天设计好**（只存本机、可删、分级证据、留出继承），否则之后的训练数据都不可信。

## 14. 浏览器基准：难度从哪里来，以及三个差点作废结果的坑

**背景**：任务都是“改文件”的编程题，不算真正的“电脑操作”。项目里已有成熟的浏览器环境：Playwright 无头浏览器、页面作用域的 `browser_observe`/`browser_act` 工具、每次全新的本地 HTTP 夹具、**独立的后台检查**（后台记录 + 恰好一次 POST + 页面读回一致才算通过）。C1 把它做成按种子生成的 stream 族。

**接入设计**
- 浏览器任务有自己的执行协议（所有臂相同）：每步一个页面动作（动作后观察 id 失效）。
- 记忆按**元素标签**记录示范（页面元素 ref 每页不同，标签能迁移）：浏览器动作结果新增 `acted`（操作、标签、值）。
- 文件技能不能驱动页面，所以浏览器任务只学记忆（`_learn` 显式跳过技能）。
- 重试臂每次尝试都在新后台上（删除上次的检查文件），否则上次的错误保存会污染这次。

**四轮难度校准**（原学生，每族 12 道校准题；`evidence/kaggle/v13–v16-c-cal-summary.json`）
| 版本 | 设计 | 表单 | 发票 | 设置 | 酒店 |
|---|---|---|---|---|---|
| v13 | 值都写在指令里，5 步 | 12/12 | 12/12 | 5/12 | 11/12 |
| v14 | 值要从页面读、按规则算 | 12/12 | 11/12 | — | 11/12 |
| v15 | 8 步/10 次调用，隐藏信息要先揭示 | 12/12 | 1/12 | 4/12 | 7/12 |
| v16 | 发票只需点一次、酒店评分下限更常见、表单两步 | 12/12（缺陷，见下） | 2/12 | — | 9/12 |

- **结论**：动作 ≤4 的单页任务，即使值要从页面读、要按规则计算，4B 学生也 92–100% 做对——**它的阅读和计算能力比我们预想的强**；真正难的是**长流程 + 需要主动揭示的信息**（隐藏行要先点“显示更多”、评分要点“详情”才显示）以及多步状态跟踪（设置题）。
- 失败都逐题核对过是真实的：无模型错误、无上下文溢出、全部正常结束。
- 最终冻结 `eval/stream_web_v1`：学习族为发票、设置、酒店（酒店 16/24=67% 高于目标区间，再加难需要 9 个动作，超出 8 步协议，**保留并如实记录偏离**）；表单只作迁移评测。

**三个差点作废结果的坑**
1. **网页样式缺陷（v16）**：表单 12/12 全过，但逐题看动作发现**一次都没点过“下一步”**——夹具样式 `label{display:block}` 覆盖了浏览器对 `hidden` 的默认隐藏，第二步字段一开始就可见。修复 `[hidden]{display:none!important}` 并加回归测试（第二步字段点“下一步”前不在观察里、点后出现）。发票隐藏行和酒店评分不受影响（这些元素没有样式规则），已逐一核对。
2. **保存与读回的计时竞争**：模型点完“保存”马上结束时，保存结果来不及显示在页面上，正确的任务会随机判失败（测试里真实出现）。修复：点保存后最多等 1 秒确认读回（`settle_saves`），与“完成门控”解耦。
3. **措辞让记忆检索失效**：最初每族句式各写各的、又带大量独有取值（人名、邮箱、城市），**同类题 TF-IDF 相似度只有 0.05–0.17**，远低于检索阈值 0.3——记忆臂几乎取不到示范，实验就测不出学习（全量测试里的相似度测试抓到）。改为每族句式共享任务词后同类最低 0.41–0.68、均值 0.58–0.83，跨族最高 0.16。另外中文句式与英文 TF-IDF 不相交，会把一族拆成两簇，所以基准只用英文。

**教训**：**我不相信只看分数的结果。**三次分数异常（太高或太低），逐题看动作都查出了真问题。基准设计里，“难度来源”要想清楚——是想测阅读、计算，还是长流程规划。

## 15. 检索到了却不照做（adoption gap）

> **10-23 更正（C4，`evidence/reports/c4/analysis.md`）**：设置题的失败主要是**接口问题**——v1 观察对没勾选的复选框不写 `checked`；改成显式（V2）后原学生设置题 1/18 → 14/18，加状态表 17/18。本条中关于设置题“知道却做不到”的解释以此为准；发票题的结论不受影响。


**背景假设**：如果学生能检索到相关的老师示范，就能照着做对（文件任务上 E-1 的轨迹记忆确实有效）。

**C2 实验**（Kaggle v17，`evidence/reports/c2/analysis.md`）：A0 同环境重复 3 次、A1、A3（Jaccard 记忆）与 A4mG（门控记忆）各 2 个流，流 44 题，检查点 22/44，每类 6 道评测题。

| 题型 | 原学生（3 次） | 学习臂 cp44（4 次运行） |
|---|---|---|
| 发票（先展开隐藏行） | 0、0、0 | 2、2、1、2 |
| 通知设置 | 1、1、1 | 0、0、1、1 |
| 酒店（评分下限） | 2、4、3 | 3、3、3、2 |
| 两步表单（迁移，从不学习） | 0、0、1 | 0、0、0、0 |
| 只读负例 | 6、6、6 | 6、6、6、6 · 零误用 |

- 合计：同类题 cp44 学习臂 20/72 vs 原学生 12/54，p=0.54，不显著。
- **发票有效果**（0/18 → 7/24，cp22 9/24），但**做对的都是同两道题**（11001、11002），运行之间强相关；按运行合并的 Fisher p=0.014 偏乐观。稳妥的说法：记忆让 6 道发票评测题中的 2 道稳定可解，原学生 3 次都没做对。
- 自动归族纯度 100%；主动求教没触发（全是失败后求教）。

**诊断（逐题看第一条提示和学生动作）**
- **检索没问题**：所有同类评测题的第一条提示里都带着记忆示范。
- **采纳是瓶颈**：发票的记忆里 9 条示范以“Show more rows”开头，但学生 6 题里只照做 1–2 次。
- **示范形式不对**：设置题的示范是**另一道题**的具体点击序列，真正要学的规则（“只点状态不对的项、只保存一次”）不在示范里；学生反而重复点同一项、保存两次。酒店题学生看不看评分与原学生无差别。

**根因**：①4B 模型对“前面对话里的示范”服从度低；②原始动作示范只描述某一道题，可迁移的是规则。

**意义**：**改变了研究方向**——与其继续优化检索，不如①把示范总结成规则（C3），②把带指导时的成功训练进权重（巩固环，R）。这也是我们和谷歌 Harness²（默认模型会照做）最关键的区别（第 20 条）。

**C3 之后的细化（10-21，见第 16 条）**：“不照做”其实分两种。
- **缺一步关键操作**（发票：没先展开隐藏行）：把这一步写成通用规则后，学生能照做，而且跨题成立（原学生 0/24 → 带规则 14/24，cp22 19/24）。
- **需要逐项跟踪状态的多步操作**（设置：每个开关先看状态、只点不对的、最后只保存一次）：老师写出的规则完全正确，注入 13–14 次，成功仅 3–4 次，分数与原学生无差别——**学生“知道”规则，但做不到**。这是执行能力的问题，不是知识的问题，是巩固环（或更强的模型）要解决的部分。

**面试时可能被追问**
- “怎么确定是不照做，而不是检索错了？”——逐题检查了第一条提示里有没有示范（全部有）和学生的实际动作（标签级 `acted` 记录）。
- “为什么文件任务上记忆有效、浏览器上无效？”——文件任务的示范是一段完整代码，几乎可以照抄；浏览器示范是另一个页面上的点击序列，要“翻译”到当前页面，需要理解规则。这是一个值得在论文里展开的对比。

## 16. 老师写规则（C3）与巩固环（R）：为什么这样设计

> **10-23 更正（C4，`evidence/reports/c4/analysis.md`）**：设置题的失败主要是**接口问题**——v1 观察对没勾选的复选框不写 `checked`；改成显式（V2）后原学生设置题 1/18 → 14/18，加状态表 17/18。本条中关于设置题“知道却做不到”的解释以此为准；发票题的结论不受影响。


**C3：老师写规则**（`core/evolution/lessons.py`，由 DeepSeek 执行器实现，第 18 条）
- 老师示范成功后，再请老师**对比“自己的成功步骤”和“学生的失败步骤”**，写 1–2 条**不含实例取值**的通用规则（何时适用、做什么、避免什么）。
- 规则按 TF-IDF 相关性门控注入提示（与记忆同一阈值），没有规则时提示与 A0 逐字节相同。
- 新对照臂：A4mGL（门控记忆 + 规则）、AGL（只有规则）。v19 在同一套冻结题目上同时重跑 A4mG 和 A0，保证同环境比较。

**C3 结果（Kaggle v19，`evidence/reports/c3/analysis.md`，花费 $0.04）**

| 臂 | 发票 cp22 | 发票 cp44 | 设置 cp44 | 酒店 cp44 | 同类合计 cp44 |
|---|---|---|---|---|---|
| 原学生（4 次） | — | 0、0、0、0 /6 | 1、1、1、0 | 2、4、3、2 | 3、5、4、2 /18 |
| 只给示范 A4mG（同环境重跑，2 流） | 0、3 | 3、3 | 1、0 | 3、3 | 7、6 |
| 只给规则 AGL | 5、4 | 1、4 | 1、1 | 3、3 | 5、8 |
| 示范 + 规则 A4mGL | 5、5 | 3、6 | 2、0 | 2、4 | 7、10 |

- **发票**：带规则两组 cp44 14/24（vs 原学生 0/24，p=8e-6），cp22 19/24；**做对的分散在不同题上**（A4mGL-s2 cp44 六道全对），而 C2 只给示范时始终是同两道。规则 vs 同环境只给示范：cp22 19/24 vs 3/12（p=0.003），cp44 差距缩小（9/12 vs 6/12，p=0.40）。
- **同类题整体**：A4mGL 17/36 vs 原学生 14/72，p=0.004；vs 只给示范 13/36，p=0.47。
- **设置题**：规则正确却无提升（第 15 条的细化：知道 ≠ 做得到）。酒店无变化。表单迁移无。
- **门控**：表单和只读负例题的提示里从未出现规则；负例全过、零误用。
- **规则质量**：全部是通用表述（例：“表格可能被折叠时，先点开所有行再计算”“先看每个开关当前状态，只点状态不对的”“比较每个候选的详情再选”）。问题：设置题的相似规则没被合并（每臂 11–22 条），检索只取前 2 条，影响小。
- **决定**：R2 的浏览器指导用“示范 + 规则”，文件任务用示范（规则目前只为浏览器任务提取）。设置题是检验“巩固能否解决执行问题”的关键题型。
- **还没排除的替代解释（10-21，读谷歌 ARTEMIS 时想到）**：设置题“做不到”也可能是**接口问题**而不是能力问题——浏览器协议每步只能做一个页面动作、每次都要重新观察，学生要在很长的对话里记住哪些开关已经点过。ARTEMIS 用“动作连发”（一轮里连续执行多个点击）和“检查员逐项核对”处理这类情况。计划 C4：给浏览器加一个按标签一次执行一串动作的工具，看原学生/只给规则在设置题上分数变不变。变了 → 失败主要是接口问题，“需要巩固进权重”的论点要收窄；不变 → 论点更站得住。论文里必须报告这个对照。
- **更具体的嫌疑（10-21 写 C4 卡时查到）**：stream 基准的浏览器观察用 `compact-v1`（`stream_run.py` 配置里记录为 `compact-v1`）——**没勾选的复选框根本不出现 `checked` 字段**，学生要从“缺一个键”推断“关着”。显式 `checked: true/false` 的 `compact-v2` 只在 10-03 用云模型、3 道开发题、各 1 次比过（两种都 3/3，`docs/experiments/2026-10-03-browser-state-diagnosis.md`），4B 学生从没在 v2 上测过。规则说“只点状态不对的”，而学生恰恰看不清哪些是关着的——这可能就是“知道却做不到”的一部分原因。C4 第一组就测 v1 vs v2（`docs/plans/cards/C4.md`）。**面试讲法**：发现一个看似是能力的失败，先查接口有没有把关键状态藏起来——这是我们自己设计里埋的坑。
- **面试怎么讲**：“我们把‘不照做’拆开了：缺一步关键操作的，写成规则就能补上，而且能迁移到同类新题；需要逐项跟踪状态的，规则写得再对，4B 模型也执行不了。前者是知识问题，后者是能力问题，后者正是我们要用训练去解决的。”

**巩固环 R**（`docs/plans/rsr-consolidation-2026-10-18.md`，借鉴腾讯 Terminal-RSI 的 RSR）
- **R1 泄漏筛查**（第 17 条）。
- **R2 带指导的新鲜执行采集**（`scripts/experiments/rsr_collect.py`）：学生在 practice 划分的新变体上带着指导（示范和/或规则）做题，每题 k 次、温度 0.6；只保留严格成功（部分得分不算）；按注入时同一函数重建并**精确删除**指导，再用 `guidance_free` 复核，删不干净就丢弃；迁移题型（F5/F6、表单）和评测种子永不进训练（代码硬拒绝）。为此给学生客户端加了可选温度（默认仍为 0）。
- **R3**：训练 LoRA-1，**不带任何指导**在冻结评测集上验收；族内超出 A0 波动范围、负例误用不增加、迁移如实报告、通用能力不退步才启用，否则回退。
- **R4**：用 LoRA-1 学生再跑一轮（递归）。

**为什么这样设计**
- 训练数据是**学生自己生成、自己格式**的轨迹，比把老师示范硬转成学生格式（原 `distill_data.py` 的做法）更贴合分布。
- 正好绕开“采纳”瓶颈：评测时不需要上下文里的指导。
- 不做强化学习（PPO + 价值网络在 T4 + 4B 上不可行），用“多次采样只留成功”（拒绝采样 / expert iteration）代替。
- 奖励只借原则：训练只用严格成功；部分进度只用于排练习顺序（差一点就成功的题优先）。

**R2 冒烟结果（Kaggle v20，10-21，`evidence/reports/r2-smoke/`）**
- 带指导、温度 0.6、每题 2 次：子集 15/16、区间 13/16、日志 11/16、CSV 9/16、发票 8/16、设置 7/16、酒店 10/16；136 次尝试 → 366 条训练样本（每次约 2.7 条，因为每次模型调用都是一条样本），删除指导后 0 条残留，系统提示与原学生只差时间戳。
- **一个必须先解释的现象**：设置题带指导时 44%，但 C3 在评测集上（温度 0）规则对设置题无效。可能原因：①温度 0.6 的采样本身就能让学生偶尔做对（这样的话，数据里的“成功”有一部分不是指导带来的）；②练习种子比评测种子容易。所以 v21 加了“不带指导、同温度、同题”的对照组——这个对照决定论文里能不能说“指导提高了产出率”。即使提升来自采样，这些成功轨迹仍然是合格的训练数据（类似 STaR 的“只留做对的”），只是归因不同。
- **v21 对照组的答案（10-21，`evidence/reports/r2/`）**：同题、同温度、每题前 2 次，带指导 71/112 vs 不带 34/112（p=1.2e-6）。分题型：子集 12 vs 2、发票 10 vs 1、日志 13 vs 5、CSV 9 vs 3、区间 14 vs 9；**设置 6 vs 6、酒店 7 vs 8——指导完全无效**。冒烟时设置题的 44% 全部来自温度采样。这与 C3 完全一致：指导只对“缺一步关键操作 / 缺一种写法”的题型有效；对“需要逐项跟踪状态”（设置）和“需要比较多个候选”（酒店）的题型，学生做对靠的是采样碰运气。论文里这两类的训练样本要归为“自己做对的样本”（STaR 式），不能算作指导带来的。
- **规模**：带指导 4 组 1900 条训练样本（0 条指导残留），对照组 193 条单独保存不进训练。
- **R3 数据划分的一个设计缺陷（我写的任务卡导致）**：卡片要求“按 task_id 哈希划分训练/验证”，每族题目少时极不均匀——一个只读负例族全部进了验证集、训练集里一条都没有。改为按族分层。教训：数据划分要按“每一类”检查，而不是只看总数。另外负例只占训练数据约 3%，可能让模型学成“总要动手改”，R3 评测的误用率会直接检验这一点。
- **一个验收漏掉的 bug**：Kaggle 阶段把任务名当成目录名，build 没跑成，且失败被静默忽略。教训见第 18 条。

**风险与停止条件**：带指导的成功率若几乎不高于 A0，采集产出率会很低——先加大 k，再考虑示范 + 规则组合，仍不足就停在 R2 并报告产出率；训练数据过于单一可能让 LoRA 只记模板，用每族上限、模板多样性和迁移测试来发现。

## 17. 泄漏筛查：防止“教答案”

**为什么需要**：规则会变成指导、指导下的成功会变成训练数据。如果规则里写着“在 Total 里填 1143”，学到的是答案而不是方法；如果训练样本里还留着指导，模型会学会“期待指导”。

**实现**（`core/evolution/leakage.py`）
- `instance_values(task)`：当前实例特有的值——浏览器任务的期望记录、预填值、发票行、酒店名/城市、便签值；文件任务的函数名、文件名、隐藏用例里的取值；所有任务指令里的引号字符串和两位以上数字；排除界面标签（“Save”“Total”这类通用词）。
- `leaks(text, task)`：按词边界匹配，数字忽略千分位逗号（`12` 不匹配 `2012`，`1143` 匹配 `1,143`）。
- `screen_lessons`：存入规则库前筛掉含泄漏的规则，并记录被拒的数量和具体泄漏值（便于分析）。
- `guidance_free`：写训练样本前检查指导文本已删干净。

**验收中发现的问题**：第一版把文件任务隐藏用例里的**普通单词**（日志级别 `ERROR`、`INFO`，CSV 列名 `email`、`name`）也当成实例值，会误删“把级别名大写，比如 ERROR”这类正常的通用规则。修复：隐藏用例里只由字母组成的单个词不算实例值（数字、多词串、邮箱、路径仍算）。

**实际运行中的误伤（C3/v19）**：每臂有 1–3 条规则被拒，被拒的值都是 “Compute”——它是某张发票的条目名，但也是普通英文动词（“Compute the total…”）。短的普通英文单词作为条目名时会误伤，待修（例如条目名只在大小写和上下文都匹配时才算泄漏）。

**教训**：**安全筛查本身也要测“误伤”**，不能只测“拦住了没有”——而且要在真实运行里再看一次被拒的内容。

## 20. 与同期工作的关系（腾讯 Terminal-RSI、谷歌 Harness²）

**腾讯 Terminal-RSI**（arXiv:2610.22192，2026-10-15）：改权重。
- RSR：已验证轨迹 → 写 runbook → 泄漏审查 → 目标模型带 runbook 重新执行 → 验证通过的轨迹删掉 runbook 做 SFT。单这一步四套基准均值 20.7% → 34.3%。
- RPR：PPO + 继承的价值网络；奖励按族归一化部分得分，并让部分得分始终低于严格成功（原奖励下失败轨迹拿走 50% 奖励）。
- 27B 模型，两阶段交替递归。

**谷歌 Harness²**（arXiv:2610.14224）：改外层（提示、护栏、记忆、工具说明、子代理、技能、脚本、插件 8 个组件）。
- 单任务内“提出–试跑–组合”：先跑参照，再提出通用缺陷和领域知识两类改动，在同一任务同样条件下试跑，**按行为对比**而不是标准答案组合改动。
- 跨任务把采纳的改动和“何时、为何有效”的经验存库。
- 强模型（GLM-5、Gemini 3.5 Flash）上最多 +11.5，超过 Meta-Harness。
- 自己承认：行为信号受运行波动和模型偏差影响。

**谷歌 ARTEMIS**（github.com/google/artemis，Android 自动化，AndroidWorld 99%+）：不是自进化系统，是一个设计得很好的 harness——动作连发、执行前检查、规划者 + 检查员（出错的步骤一直留在上下文里直到纠正）、历史压缩成可检索片段；用大模型。对我们的意义：提醒设置题的失败可能是接口问题（见第 16 条“还没排除的替代解释”）；它路线图里的“端侧轻量视觉模型”与 Kage 的本地小模型方向一致。

**我们的位置**
- Kage 两层都做：L0–L2 对应 Harness² 的方向，L3 巩固环对应 Terminal-RSI 的 RSR。
- **我们有它们都没有的证据**：外层改进默认模型会照着指导做，在强模型上成立；**4B 学生检索到指导却常常不照做**（第 15 条）。论文主张：*harness-level self-improvement presumes instruction adoption; small local models violate it, and consolidation recovers it*（待 R3 结果支撑）。
- 时间上：我们的“上下文蒸馏”计划写于 10-16（工作日志），Terminal-RSI 10-15 挂出，Harness² 更早一些但我们 10-20 才读到；巩固环是读到 Terminal-RSI 之后才明确借鉴的，论文里如实写明借鉴关系。“带提示做成功再去提示训练”本身有更早的先例（上下文蒸馏、STaR、expert iteration），不是任何一家独有。

## 22. 通用决策模型（Jev / THX-01 / Clef）：小模型只会分类；大模型会抽取，但整体判断仍不可靠

**背景**：10-21 用户提议引入“只输出概率”的决策模型（TypeSafe Jev、HAL-X THX-01、Cloudflare Clef）：给状态 + 带类型的问题，输出校准概率，几十毫秒一次。直觉是：设置题的问题出在决策，那就让专门的决策模型来做。

**做法**：先测再接。THX-01 免费、Apache-2.0、322M，本地 MPS 零样本跑；题目全部由 Kage 的种子生成器在评测种子上生成，标准答案来自生成器（`evidence/reports/decision-thx01/report.md`）。Clef 需要用户自己的 Cloudflare token，暂未测。

**现象 / 证据**
- 粗粒度语义分类可以：14 类路由 0.86（随机 0.07），置信 ≥0.9 的 77 题里 0.96，ECE 0.04。
- 写入/只读判断 0.82，只比多数类 0.71 高一点；“选一家酒店并保存”12 次全被判成只读。
- **Kage 真正卡住的决策它全部在基线水平**：设置状态检查 0.50（80 题全答“满足”，一半置信 ≥0.9）、下一步动作 0.42（75/80 选“保存”，总选保存是 0.44）、逐项意图抽取 0.45（80 个任务只有 5 个全对，换成是非题问法也一样）。

**根因**：这类模型擅长“这段文本整体像哪一类”，不擅长把一句话拆成逐项约束、再和另一份状态逐项对照——这正是设置题需要的“逐项状态跟踪”。通用模型的通用性在粗分类，不在结构化比对。

**解决思路**
1. 比对本身不该交给模型：界面抽象成状态表后，“满足没有 / 还差哪项”是确定性的程序 diff（并入 C4，先做）。
2. 模型只负责“自然语言请求 → 逐项目标”这一步，这才值得训练一个小决策模型（以 THX-01 为底座在 Kaggle 上微调）。
3. **陷阱**：生成器模板很规整，一个正则就能 100% 抽取意图（本测试标准答案就是这样得到的），在同模板数据上训练到高分什么也证明不了。必须用**没见过的说法**（老师改写、真实请求）做测试集。

**加测 Clef（27B，Cloudflare，同一份题，用户自己的账号，$0.0565，在免费额度内）**：路由 1.00、写入判断 0.95、发票规则 1.00、下一步动作 1.00、逐项意图 1.00——规模一上来，零样本基本都会了。但**直接问“当前状态满足任务吗”仍只有 0.64**（状态其实正确的题只答对一半）；同一个模型逐项抽取、再由程序比对，T3/T4 都是 1.00。这把“比对交给程序、模型只做逐项抽取”从推论变成了证据。注意题目来自规整模板，满分不代表真实请求。

**状态**：零样本结论已有证据（`evidence/reports/decision-thx01/report.md`）；界面抽象 + 程序检查器排在 R3 之后（C4）；自训小模型的路线：Clef 给老师改写过的请求打逐项标签 → 蒸馏进本地 THX-01 底座 → 在留出说法上测。Clef 只用于基准数据，每天控制在免费额度内。

**面试怎么讲**：“我们没有因为它火就接进来，先用自己生成器造了 900 道带标准答案的题测零样本——小模型分类很好、状态比对完全不会，而且会自信地错；27B 的 Clef 逐项抽取全对，但直接问整体是否满足仍只有 0.64。于是把问题拆开：比对交给程序，模型只做语言到结构的转换；并且指出在模板数据上自训会虚高，测试必须换说法。”这体现的是“先量后接、找准瓶颈、警惕虚高”的判断。

## 23. R3 巩固：同类题大幅提升，迁移却变差——SFT 会放大“风格”

> **10-23 更正（C4，`evidence/reports/c4/analysis.md`）**：设置题的失败主要是**接口问题**——v1 观察对没勾选的复选框不写 `checked`；改成显式（V2）后原学生设置题 1/18 → 14/18，加状态表 17/18。本条中关于设置题“知道却做不到”的解释以此为准；发票题的结论不受影响。


**做了什么**：把 R2 的 1900 条“带指导做成功、删掉指导”的样本，用 LoRA（rank 16，约 1900 万参数）训练进 4B 学生；评测时**不给任何指导、记忆、规则**，与原学生在同一 Kaggle 会话里各跑 3 次（`evidence/reports/r3/analysis.md`）。

**现象 / 证据**
- 文件学过的族 **64/72 vs 30/72（p=2.6e-9）**：子集选择 18/18 vs 0/18，CSV 18 vs 6；比 E-1 带技能库/记忆（81–88%）还高，而且上下文里什么都没有。
- 网页 21/54 vs 10/54（p=0.033），主要是发票 **0 → 8/18**——C2/C3 里“检索到却不照做”的那条规则，现在长进了权重。
- 设置、酒店仍无提升：R2 已显示指导对这两族无效，巩固只能巩固“带指导能做对”的东西。
- **迁移族 15/36 → 1/36（p=1e-4）**；负例 `lookalike_readonly` 被改 2 次；通用 30 题答案逐字相同。

**根因**：L3 在每一次工具调用前都不写推理了（135/135 空说明，原学生 10/157）。训练数据里空说明只占 36%（522/1439），SFT 却把它放大成 100%——学会了“直接动手”这种风格。学过的题这样更快更准；新题少了“先把规则逐条列出来”，就写出 `encode("ascii")` 这种会抛错的代码。

**怎么确认适配器真的生效**（面试常问“你怎么知道不是噪声”）：同一题的第一次模型输出，原学生两次运行之间 28–29/48 相同（GPU 非确定性），L3 两次之间 45/48，L3 与原学生之间只有 2–3/48；每一次 L3 运行都高于每一次原学生运行。

**解决方向（R4 前）**：只保留或加重带推理说明的目标；混入原学生自己做对的无指导样本防遗忘；负例上采样；更小学习率/1 轮，比较迁移。迁移族永不进训练（否则就测不出这件事）。

**R3b-1 缩放（v27，`evidence/reports/r3b/scale.md`）**：同一适配器推理时只加 0.25/0.5/0.75。学过的族随缩放单调上升（文件 0.5 时 45/72 vs 原学生 40/96，p=0.008），迁移在 0.5→0.75 之间断崖式掉到 0；0.5 时迁移 11/36 vs 20/48（p=0.36，不再显著下降）。缩放是不用重训的“提升–遗忘”旋钮，但不是免费午餐（0.5 只保住约一半提升，负例每次误用 1 次）——根因要靠数据修复（R3b/R3c）。**面试讲法**：“我们画出了权衡曲线，而不是只报一个点；缩放能找到一个折中点，但它掩盖不了训练数据的问题。”

**R3b（v29，`evidence/reports/r3b/analysis.md`）**：回放（AgentNet 800 + Toucan 600 + 原学生自己的样本）+ 删除无推理目标。迁移完全恢复（15/36，与原学生无差别；R3 是 1/36），负例零误用，网页学过的族比 R3 还好（31/54 vs 21/54，发票 13/18）；但**文件学过的族的提升消失**（34/72 vs R3 64/72）。原因：被删掉的“无推理目标”恰恰是文件题写答案的那一步（`write_file` 202 条无推理、101 条有推理）。**教训：风格问题要修样本（补写推理），不要删样本。** 下一步 R3d：老师给这些步骤补写 1–2 句推理（STaR 式 rationalization），再加回放。**面试讲法**：“第一次修复把病根和疗效一起切掉了——数据过滤一定要看被过滤掉的是什么。”

**R3c（v30，`evidence/reports/r3c/analysis.md`）**：用 LESS 梯度影响力挑回放（目标 = 原学生自己的推理样本 + R2 验证集），选出 879 条（多为 Toucan）。结果迁移又掉到 2/36（随机回放 R3b 是 15/36），学过的族与 R3b 相当。**根因**：LESS 挑“和目标最一致”的数据，适合学新任务；而回放防遗忘靠的是“和训练任务不同”的那部分分布——目标选错了，方法再好也是反效果。**面试讲法**：“用户让我用最好的数据挑选方法，我用了 LESS，结果更差；这不是方法不好，是我把‘学新东西’的工具用在了‘别忘旧东西’的目标上。选方法前先想清楚优化的是哪个目标。”

**R3d（v31，`evidence/reports/r3d/analysis.md`）**：526 条无推理目标由老师补写推理（$0.106），回放用 LESS 的 879 条。文件学过的族回到 R3 水平（62/72），每次调用前都写推理、零误用——“修样本而不是删样本”成立。**但迁移仍是 6/36**：学生已经在写推理，迁移照样掉——所以本条最初的根因（“SFT 放大了不写推理”）只是症状之一。现在的两个候选：LESS 回放不防遗忘；或把文件族的写法学得太强、套用到同样“写文件”的迁移族。R3e（补写推理 + 随机回放）用来区分。**面试讲法**：“我们的第一个根因解释被后续实验部分推翻了——这是好事，说明实验设计能证伪自己的假设。”

**R3e（v32，`evidence/reports/r3e/analysis.md`）——收官**：补写推理 + R3b 的同一份随机回放。文件学过的族 **65/72（最高；vs 原学生 p=5e-12）**，误用 0，通用 28/30；**迁移 1/36**（vs R3b 15/36，p=1e-4）。五个版本对齐后结论清楚：**迁移只在“文件题写答案”步骤（约 300 条 `write_file`）留在训练里时塌**，与回放方式（随机/LESS）、是否写推理都无关——**提升和遗忘来自同一批样本**；R3b 的随机回放“保住迁移”只是因为那一版没学到会伤害迁移的东西。逐条看轨迹：①迁移题写出的代码本身变差（`slugify` 用 `encode("ascii")` 会抛错、用 `split("_")` 代替正则）；②**写后读回验证**从原学生 48/72 降到所有训练版本的 0——训练轨迹在检查器通过后就结束，学生学会“写完即停”，失去了原学生“写 → 读回 → 改”的自我修复路径；③“先读输入”不是区别（R3 迁移题 36/36 都先读了，仍 1/36）。回放数据（桌面操作文字 + MCP 调用）里没有写代码样本，覆盖不到被覆盖掉的能力。**修复方向（记为后续工作，训练线到此为止）**：用原学生自己在其它编程题上的成功解做自蒸馏回放；训练轨迹保留写后验证步骤；部署上按任务族门控启用适配器。**面试讲法**：“我做了五个版本的消融，最后发现提升和遗忘是同一批样本的两面——回放只能保护它覆盖到的能力，我们的回放里没有写代码，所以保不住写代码。下一步不是换更聪明的选样方法，而是让回放覆盖被伤害的能力，并且别让训练数据教会模型‘写完就停’。”

**流水线教训**：这次训练前在 Kaggle/Colab 上连续踩了 8 个坑（层名、转换器、torchao、显存、fp16 静默不更新、空闲回收……），见 runbook 14–22。最值钱的两条：冒烟必须和正式运行走同一条路并检查真实产物（B 矩阵是否非零）；训练产物立刻落到持久存储。

**面试怎么讲**：“我们证明了巩固能把上下文里的指导变成权重——同类题从 42% 到 89%，不再需要任何提示；但也发现了代价：SFT 放大了训练数据里‘不写推理直接动手’的风格，新题型反而变差。我们用逐题第一步输出的一致性确认了效果来自适配器而不是 GPU 噪声，并定位到具体的失败代码。这说明自进化 Agent 的权重更新必须同时监控迁移和行为风格，而不只是看训练题的分数。”

## 24. C4：一个字段让设置题从 1/18 到 17/18——先排除接口，再谈能力

**背景**：设置题（勾选/取消通知开关）在 C2、C3、R2、R3 里一直学不会：老师写的规则正确（“只点状态不对的，最后保存一次”），学生检索到了也做不对；我们把它解释成“知道 ≠ 做得到”，作为“需要把能力巩固进权重”的论据之一。读谷歌 ARTEMIS 时意识到可能是接口问题，C4 用对照实验检验。

**现象 / 证据**（Kaggle v28，原学生、无任何指导，网页评测集各 3 次）
- 观察格式 v1：没勾选的复选框**不写** `checked` 字段（只写勾选了的）。设置题 **1/18**。
- v2：每个复选框显式 `checked: true/false`。设置题 **14/18**（p < 1e-5）。
- v2 + 打包（只留最新页面）+ 状态表（每个开关 on/off 一行）：**17/18**；每次调用输入从最长 7.5k token 降到 4k 以内。
- 代价（**第二轮更正**：不显著，p=0.47；学生本来就不看详情）：打包后酒店题 7/18 → 4/18，当时以为是需要回看先前展开的详情。

**根因**：这是我们自己设计的“精简观察”埋的坑——为了省 token 省掉了 `false` 值，结果对 4B 学生来说，“没有这个键”不等于“关着”。规则要求“只点状态不对的”，学生恰恰看不出哪个状态不对。

**解决与影响**
- 新默认接口：v2 + 状态表；打包用于长任务，但要把被归档页面里的关键信息写进动作摘要。
- **更正之前的结论**：设置题不再作为“知道却做不到”的证据（insights 15/16/23 已加更正）；发票题仍是真正需要规则/巩固的例子（0 → 14/24 → 8/18 不带指导）。
- 浏览器基准按 v2 协议重建基线，v1 结果保留并标注协议版本。

**状态**：第二轮完成（v33，`evidence/reports/c4/round2.md`）。v2 基线 41/90，设置题 18/18；Clef 逐项抽取目标 48/48 正确，但保存前检查器 59 次检查 0 次拦截——接口修好后设置题已满分，检查器没有发挥空间（也无误拦）。**更正第一轮**：“打包让酒店题下降”不成立（7 vs 4/18，p=0.47）；逐条看轨迹，学生打包前后都只点 3 下、从不打开详情看评分——酒店题是流程知识问题。R3e 适配器在新接口下发票 7/18（原学生 0/54，p=2e-5），合计 47/90 最高：巩固学到的东西换了接口仍保留。**面试补充**：“我们还做了一个检查器，抽取准确率 100%，但实验显示它在这个基准上没用——因为接口修好后已经没有它能拦的错误。我们如实报告‘没有提升’，而不是挑一个数字。”

**面试怎么讲**：“我们曾经把一个失败归因成模型能力不足，还用它支撑论文主张。后来做了一个很便宜的对照：只改观察里一个字段，失败率从 94% 降到 6%。教训是：在自进化系统里，先确认 agent 看到的东西是对的，再讨论它学没学会——否则你会去训练模型解决一个接口 bug。这也是我们论文里最诚实、也最有说服力的一段。”

## 25. G0 桌面：老师规则放进提示里没用，让学生先把规则落到本题才有用

**现象 / 证据**（`evidence/reports/g0/analysis.md`，本机 Mac，辅助功能接口，4B 学生，每臂每题 3 次）
- 基线 19/30：计算器加/乘/除 9/9；带括号连算 1/3（按 `15 + 27 × 3 =` 得 96）；TextEdit 2/9（丢末尾换行）；系统设置只读 7/9（两次接口问题）。
- 老师对失败写 4 条通用规则（$0.0005）。在 5 道**没见过的变体**上：无规则 3/15；**规则放系统提示 3/15（完全没用）**；只要求先写计划 6/15；**规则放在任务旁 + 先写“每条规则怎么用”的计划 10/15**（vs 无规则 p=0.025）。
- 计算器的提升大多来自“先写计划”（1/6 → 4/6 → 5/6）；TextEdit 只写计划没用（2/9），规则 + 计划到 5/9——规则内容（末尾换行）在这里起作用。
- 规则能类推：先减后除的题，规则只写了加法和乘法，学生在计划里写“先按等号得到 36，再除”。

**根因**：4B 学生读到规则不会自动套用到眼前这一步（与 C2/C3“检索到却不照做”同源）；要求它在动手前把规则翻译成本题的具体操作（确切按键顺序、确切文字），规则才进入行动。

**状态**：演示闭环成立（不会 → 求教 → 规则 → 新题会）。**TextEdit 后续（同日）**：改接口后 4/18 → 17/18（p=2e-5），不靠规则——`replace_text` 让改错字 0/6 → 6/6；追加/写入的失败是学生在 JSON 参数里写不对换行（漏最后一个，或多转义成字面 `\\n`），规则+计划救不了（4/12），改成“给出行的列表、换行由程序写”（`append_lines`/`set_lines`）后 17/18。**两类失败要分开治**：流程知识（计算器先按等号）靠规则+计划；表达困难（精确写控制字符）靠接口。

**面试怎么讲**：“桌面上我们遇到两类失败。一类是流程知识，比如计算器要先按等号——老师写的规则是对的，但放在系统提示里小模型一条都不用；我们做了对照，发现关键是让它在动手前把规则落到这道题——写出确切的按键顺序。这样新题从 3/15 到 10/15。另外我们还做了‘只写计划不给规则’的对照，拆开了‘计划’和‘规则内容’各自的贡献：计算器主要靠计划，文本编辑靠规则内容。另一类是表达困难：4B 模型在 JSON 参数里写不准换行，规则再多也没用；我们把工具改成‘给出行的列表’，TextEdit 从 4/18 到 17/18。所以失败要先分类：知识问题教，接口问题改。”

## 26. 桌面助手：小模型要“程序替它找、程序替它限”——一次差点改坏真实文件的事故

**现象 / 证据**（`evidence/reports/d0`、`d1`、`d2`）
- 改打开的文档：模型编路径（`/Users/yourname/...`）；给了“列出打开文档”的工具也不用（≈2/10）；服务端先查出真实路径附在请求后、文档类请求只给文档工具 → 9/10，加写入范围后 11/11。
- 打开应用：9 句里 5 句没调用工具就回答“已打开”；程序直达通道 → 20/20。
- 读日历：Python 调 EventKit 被系统**静默拒绝**（无用途说明不弹窗），AppleScript 不展开重复日程；自带用途说明的小助手 app 才正确（5/5，含夏令时切换日）。
- **事故**：说了一个不存在的文件，服务端把所有打开的文档列给模型，模型对用户 VS Code 里的真实代码执行了 3 次 `doc_replace`（恰好都是把一行换成同一行，内容未变，已恢复修改时间）。

**根因**：4B 模型会编信息、会在没动手时声称完成；而“找不到就退而求其次”的程序逻辑把风险放大了。

**解决**：信息由程序给（真实路径、日历内容）；确定的动作由程序做（打开应用、读日程）；**每轮写入范围由程序定**（只含用户点名且存在的文件），范围外拒绝；拒绝无变化的“修改”；使用日志把“声称完成但没调用工具”单列出来。

**状态**：D0–D2 完成；使用日志上线。

**面试怎么讲**：“把小模型接到真实电脑上，最大的风险不是做不到，而是做错地方还说做好了。我们的一次测试里它差点改了用户的代码文件。修法不是在提示里叮嘱它，而是让程序决定它这一轮能碰哪些文件——这和最小权限原则是一回事。”

## 27. 微信发消息：没有接口的应用，每一步都要“读回来核对”再往下走

**现象 / 证据**（`evidence/reports/d4/analysis.md`、`d4b-dialog.txt`）
- 微信 4.1 只暴露 6 个辅助功能节点，读和发都只能靠截图 + 本机 OCR + 键盘。
- 第一次真机发送：在搜索框按回车，打开的是“搜一搜”网页搜索而不是联系人；因为发送前要 OCR 读回聊天标题并与收件人比对，这次**没有发出任何内容**。
- 改为 OCR 搜索弹窗、只点“联系人/群聊/功能”分区下名字完全一致的条目后：文件传输助手 3/3、小号 4/4 送达；不存在的名字即使用户说“确认”也不发。
- 送达校验最初只看下半屏，短聊天里新消息在上方，2 条真送达被报成“没认出”→ 改为比较发送前后同文本气泡数，再测 2/2 正确。

- 第一次录演示：多按的一次 Esc 把微信主窗口关了（微信 4 在无可取消时 Esc 关窗口），之后所有名字都被判成“没有这个人”；紧接着用户说“确认”，此时并没有待发消息，这句落到 4B 模型，它回答“已发给 Wenbo yan”——**完全编造**，实际什么都没发（`docs/worklog/2026-10-claude.md` 10-25 D6 条）。

**根因**：界面操作的结果不可预期（同一个回车键在不同界面含义不同），只按“预期流程”盲打会把消息发给错的人；校验区域按“通常情况”设定也会误报。程序通道之外的一句短回复（“确认”）也会被小模型接住并编造结果。

**解决**：操作前用 `open -a` 确认微信主窗口在屏上，Esc 只在弹窗存在时按；微信回合后的裸“确认/取消”由程序回答，不交给模型；使用日志把无工具调用的“已发给”记为“声称完成但没动手”。每个不可逆动作前都有程序核对（标题 = 收件人才粘贴正文）；默认先问用户“确认”，只有用户指定的两个自己的账号免确认；送达用前后差分而不是位置猜测。

**状态**：D4 读 + 发完成。

**面试怎么讲**：“没有 API 的应用只能模拟操作，我的原则是‘每一步做完都读回来核对’。第一次实测按回车就跳到了网页搜索，正是标题核对把这次错误发送拦住了。我把这类核对看成给不可逆操作加的断言。”

## 28. 慢的不是模型能力，是让模型做了“选择题”：决策模型选、程序做

**现象 / 证据**（`evidence/reports/d5/clef-routing/README.md`）
- 演示里“知乎热榜前三”14 秒：本地 4B 选命令 4.2 s、OpenCLI 取数 4.2 s、4B 把列表复述一遍 5.7 s。
- 先试正则直达：7 句错 2（“关于考研的热门问题”列了热榜；“排行榜第一名”给 5 条）——用户也指出这像作弊：只认写死的说法。
- 换成 Clef 做选择（哪个命令、要几条、搜索词从程序切出的候选里挑、是否需要读内容），程序执行并原样列出：留出 10 句新说法选命令 10/10，端到端 14 s → 4.5 s；拿不准或要总结比较的退回本地模型。
- “原样列出就够了吗”这种整体判断只有 8/12、置信 0.6–0.8；改问具体项“是否要求总结/比较/挑最高/筛选”后 11/12——和第 22 条“整体判断 0.64、逐项 1.00”一致。

**根因**：日常操作大部分步骤是“从几个选项里挑一个”，让 4B 生成式模型边想边写来做选择既慢又不稳；而把结果复述一遍对列表类请求没有增加信息。

**解决**：决策模型只负责选择、给出置信度；程序执行与排版；置信度不足或需要理解内容时交给本地模型。使用日志记录每次由谁决定（`opencli_clef` / `opencli_site`）。

**状态**：站点请求已接入；公开榜单再加短时缓存（热榜 5 分钟、搜索 30 分钟，标注数据时间，可“刷新”），重复问 0.4 s。同样思路可推广到其它意图路由（目前的日程/邮件/微信等快速通道仍是正则）。

**面试怎么讲**：“我先量了 14 秒花在哪，发现 10 秒是让小模型做选择题和复述。用正则直达能快但不泛化；改成专门的决策模型做选择、程序执行，留出说法上命令选择全对、延迟降到三分之一，并且保留置信度阈值，不确定时退回生成式模型。问法也有讲究：问具体项比问整体判断准得多。”

## 29. 意图路由：正则在新说法上只有一半，决策模型 30/30；“慢”的大头在提示长度和复述

**现象 / 证据**（`evidence/reports/d7/README.md`）
- 原来的快速通道靠手写正则判断意图：两次留出集只认对 15/30、16/30，还会误判（“明天会下雨吗”→日程，“B站是哪一年成立的”→网站）。
- 每轮一个 Clef 选择题（约 0.3 秒，与其它检查并行）：两次留出集都是 30/30；加 0.8 阈值后，不确定的交给本地模型通用流程（开发集里“退回正则”会把“知乎是什么网站”当成网站请求，所以改成退给模型）。
- 分阶段计时找出三处慢：天气要求句中含“天气”二字，否则走网页搜索 36 秒 → 路由后 0.8 秒；知识问答走工具循环 16 秒且答“查不到” → 精简提示直接回答 2.3 秒且正确（原提示 2,200–3,600 token，读提示就 7–11 秒）；“知乎上大家在聊什么”27 秒 → 4.8 秒（不让 4B 重新选命令和复述十条）。

**根因**：小模型本机推理每秒约 26 个输出 token、300 个输入 token，时间几乎全花在“读长提示”和“写长回答”上；正则路由则把大量请求送进了最慢的通用流程。

**解决**：决策模型路由 + 处理器只取参数；闲聊用约 300 token 的固定短提示（前缀可被推理服务缓存复用）；网站请求即使命令置信度不高也执行首选命令，只让本地模型读结果简短作答。

**状态**：D7 完成；正则链保留为决策模型不可用时的后备。教训：新建 `core/intent_router.py` 时覆盖了仓库里同名的已有文件（以及同名测试），全量测试时发现并从 git 恢复，新模块改名 `desktop_router.py`——建文件前先确认路径不存在。

**面试怎么讲**：“我们先建了带反例的评测集，用留出集比较：正则一半、决策模型全对。然后按分阶段耗时去找慢点，发现瓶颈不是模型‘想’得慢，而是提示太长、回答太长，以及路由错把简单问题送进工具循环。最典型的是一个知识问答从 16 秒错答变成 2 秒答对。”

# 第三部分 面试可能的追问

以下是可能被问到的问题，以及回答时可以引用的条目（面试时再按需要组织语言）。

- **“介绍一下这个项目。”** → 0.1 目标与约束（为什么 4B + $4 有研究价值）、0.2 架构、0.4 时间线，然后挑 2–3 个发现（第 5、15、9 条）。
- **“项目最大的挑战是什么？”** → 第 15 条（以为问题在检索，证据说在采纳，于是改了方向）；或第 7 条（温度 0 也有噪声，很多“提升”不成立）。
- **“有什么失败的地方？”** → 第 9 条（L2 选中噪声）、第 5 条（技能不比记忆强）、第 8 条（主动求教没机会发挥）、第 10 条（自练无显著收益）。讲成“学到了什么、改了什么规矩”。
- **“怎么证明你的方法有效？”** → 0.3 评测纪律（冻结清单、种子分区、检查点关学习、对照臂）+ 第 7 条（原学生重复、配对检验、区分两类结论）+ 第 19 条（证据可复算）。
- **“你怎么发现问题的？”** → 第 2、14、15 条：分数异常时逐题看轨迹和动作，而不是只看汇总数字。
- **“如果重来会怎么做？”** → 一开始就测系统噪声（第 7 条）；一开始就把基准难度来源想清楚（第 14 条）；更早做逐题动作诊断；晋级规则一开始就要求重复验证（第 9 条）。
- **“成本是多少？怎么控制的？”** → 第 11 条（账本机制、缓存共享、花费明细）、第 12 条（免费 GPU）、第 18 条（执行器成本实测）。
- **“隐私怎么处理？”** → 第 13 条（只存本机、可删、分级证据、留出继承、脱敏导出）、第 17 条（泄漏筛查）。
- **“和大厂的工作比有什么价值？”** → 第 20 条：同一问题在极端资源约束下的答案，以及“小模型不照做”这个它们没有的发现。
- **“你是怎么用 AI 工具开发的？”** → 第 18 条（规划/执行分工、验收纪律、安全隔离与验证、成本实测）。
- **“你犯过什么错？”** → 第 21 条，重点讲怎么发现、怎么更正、怎么防止再犯。
