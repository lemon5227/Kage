# C4: interface control — is the settings failure an interface problem or a capability problem?

Executor: Claude (writes the code). Runs after R3's evaluation is finished (do not change browser/experiment code
that R3's A0/L3 jobs use before then). No teacher calls.

## Why
C3 (v19) and R2 (v21): the student receives the right rule for `web_prefs` ("only click checkboxes whose current
state differs from the target, save once") but its pass rate does not move (C3 13–14 injections, 3–4 passes, no
difference from A0; R2 guided 6 vs unguided 6). Our paper explanation is "knows but cannot do → needs
consolidation". Three alternative explanations must be ruled out first:

1. **Observation format.** The stream benchmark uses `compact-v1` (`scripts/experiments/stream_run.py`
   records `'observation': 'compact-v1'`): a checkbox that is NOT checked has no `checked` field at all, the student
   must infer "off" from a missing key. `compact-v2` keeps `checked: true/false` for checkboxes/radios.
   The only v1/v2 comparison (`docs/experiments/2026-10-03-browser-state-diagnosis.md`) used the cloud model,
   3 dev tasks, 1 run each, and the 4B student was never tested on v2.
2. **State tracking over a long history** (ARTEMIS; 16k context): the student must remember which boxes it already
   clicked across up to 8 steps.
3. **No completion check**: nothing tells the student that a requested item is still wrong before it saves.

Zero-shot THX-01 cannot do this comparison (`evidence/reports/decision-thx01/report.md`: state check 0.50,
next action 0.42), so the checker is a program, not a model.

## Arms (eval only, cp0, arm A0 unless stated; frozen `eval/stream_web_v1/eval.json`, 3 runs each, same session)
| Arm | Change |
|---|---|
| V1 | as today (`compact-v1`) — baseline, re-run in the same session |
| V2 | `compact-v2` (explicit checked) |
| ST | V2 + a short **page state table** prepended to each observation (label → on/off / field → value, hidden rows count), and history packed to "latest full page + one line per earlier action" (target ≤ 8k context) |
| CK | ST + **program checker**: after each action, if the page has a pending save or the student says done, a deterministic check against the instruction's per-item goals (parsed from the instruction by the same rule the family generator uses — benchmark-only oracle, recorded as such) returns "still wrong: X" | 
| ST+L | ST + the v19 A4mGL lessons (does the rule start to work once the state is visible?) |

`CK` is an upper bound with an oracle goal parser and is reported as such; the deployable version needs a
learned "request → per-item goals" model (see roadmap; tested on held-out phrasings).

## Measures
- Pass per family (web_prefs is primary; web_invoice / web_catalog must not regress; web_lookup misuse must stay 0;
  web_form transfer), Fisher vs V1 per family, A0-replicate variance as in C3.
- For web_prefs failures, classify every failing run: wrong item clicked / required item missed / correct item
  clicked twice / saved early / never saved / ran out of steps (from `acted` entries + final record).
- Context: input tokens per call, max context used; V1 vs ST.

## Decision rule
- V2 ≫ V1 on web_prefs → the main C3/R2 finding was partly an interface artefact; correct insights 15/16 and the
  paper, and re-baseline the browser benchmark on v2 (new frozen protocol version; old results stay as v1).
- ST/CK ≫ V2 → state tracking / checking is the bottleneck; build the deployable checker.
- No arm moves web_prefs → the capability explanation stands, with three alternatives now excluded.

## Implementation notes
- `observation_format` already exists in `BrowserTaskSuiteRunner`; thread it through `stream.browser_chain` and
  `stream_run.py` (`--observation compact-v1|compact-v2`, default unchanged) and record it in the run config.
- State table and history packing: new optional flags, default off; existing protocol unchanged.
- Tests without network/GPU; Kaggle phase `c4` with 15 jobs (5 arms × 3 runs), distinct ports, `KAGE_CTX` per job.
