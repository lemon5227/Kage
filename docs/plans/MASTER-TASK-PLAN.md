# Kage 总任务规划（唯一执行入口）

更新：2026-10-14 · 状态：**生效中**
项目目标：**一个会自进化、自演化、会主动交互的个人 Agent**——它能操作电脑，能从失败和示范中学到可复用的能力，能改进自己的模块，并且会在合适的时候主动找用户说话。

> 这份文档是**执行入口**。任何模型（包括便宜模型）领取任务时，只需要读：本文的「执行规则」+「测试环境」+ 自己领取的那一个任务小节 + 小节里列出的文件。不要把整个 `docs/` 塞进上下文。
>
> 审查依据见 [2026-10-14 项目审查报告](../audit/2026-10-14-project-audit.md)。研究线（E/C 编号）的详细规格仍在 [E/C 任务队列](task-queue-2026-10-01.md) 与 [执行交接](execution-handoff-2026-10-03.md)，本文只给出领取顺序和落地步骤。

## 一、执行规则（每个任务都必须遵守）

### 1.1 开始前

1. `git status --short` 必须干净；`git pull origin <当前分支>` 拿到最新代码。
2. 确认 Git 身份是项目所有者本人，**不要把 AI 加成作者或合作者**：
   ```sh
   git config user.name  "wenbo"
   git config user.email "yan2000926@gmail.com"   # 作者的 GitHub 邮箱，提交才会归属到作者账号
   ```
   提交信息里**不要**写 `Co-Authored-By`、`Generated by`、模型名、会话链接等任何 AI 署名行。
3. 在本文「三、任务总表」找到状态为 `待领取` 且依赖都已 `完成` 的最小编号任务；检查「环境」列与你的机器是否匹配（例如 `macOS` 任务不能在 Linux 上做）。
4. 从 [日志模板](../task-logs/TEMPLATE.md) 复制一份为 `docs/task-logs/Txx-简短英文名.md`，**先写好"目标/计划"再动代码**。

### 1.2 实施中

- 只改任务小节"涉及文件"里列出的文件；确实需要改别的文件，在日志"偏离计划"里写清原因。
- 先写失败的测试，再改代码让它通过（红 → 绿）。
- 每完成一个步骤，就在日志"过程记录"里追加一行：做了什么、改了哪个文件、怎么验证的。
- 遇到做不到的验收项：**不要伪造、不要删测试、不要把失败改成跳过**。在日志里写"阻塞原因 + 已尝试的办法"，任务状态标 `阻塞`，然后提交推送。

### 1.3 完成后

1. 跑任务小节里的"聚焦测试"，再跑一次「测试环境」里的全量测试；把命令和结果（通过/失败数量）贴进日志。
2. 把本文「三、任务总表」里该任务的状态改为 `完成`（或 `阻塞`），在"日志"列填日志文件链接。
3. 一个任务一次提交（代码 + 测试 + 日志 + 总表状态一起）。提交信息格式：
   ```
   <type>(<范围>): Txx 一句话说明

   做了什么（2–4 行）
   验证：<测试命令> → <结果>
   ```
   `type` 取 `feat` / `fix` / `docs` / `test` / `chore`。
4. 推送：`git push -u origin <当前分支>`。网络失败最多重试 4 次（间隔 2s/4s/8s/16s）。**每个任务完成都要推送一次**，不要攒到最后。

### 1.4 不可违反的底线

- 不得让模型自己批准危险操作；不得在主进程 `import`/`exec` 模型生成的代码。
- 不得把未经晋级（promotion）的技能/模块默认装进日常主链。
- 不得把实验"跑过一次"写成"能力已实现"；结果可以是负结果，照实记录。
- 不得在日志/提交中打印 API key 或私有配置内容。

### T02 危险操作确认闸门与技能写入路径修复

- **目标**：危险操作只能由用户确认放行；模型不能自己放行；确认流程出错时默认拒绝；技能文件不能写到技能目录以外。
- **背景**：`core/tool_executor.py` 中 `if arguments.get("confirmed") is True: pass` —— 参数由模型生成，等于模型可自签确认（评审 B2）。确认回调抛异常时只打 warning 然后**继续执行**。`get_security_level` 对未知工具返回 `SAFE`。`core/tools/agent_ops.py::proactive_agent` 直接 `os.path.join(sd, f"{skill_name}.md")`，可路径穿越。
- **涉及文件**：`core/tool_executor.py`、`core/tool_registry.py`、`core/tools/agent_ops.py`、`tests/test_security_hardening.py`（追加用例）。
- **实施步骤**：
  1. 先写测试（全部应先失败）：
     - 无回调时执行 `fs_trash` 并带 `{"confirmed": True}` → 结果 `error_type == "NeedConfirmation"`，handler 未被调用。
     - 回调抛 `RuntimeError` → 结果 `outcome == "denied"`（或 `error_type == "UserDenied"`），handler 未被调用。
     - 回调返回 True → handler 被调用（保持 `pending_handlers` 的用户确认路径可用）。
     - `ToolRegistry().get_security_level("不存在")` 返回 `"DANGEROUS"`。

  2. `core/tool_executor.py`：删除 `confirmed` 参数旁路分支；`require_confirmation` 抛异常时按"用户拒绝"处理（返回 `UserDenied` 结果并写审计日志）。

  4. `core/tools/agent_ops.py::proactive_agent`：复用 `core/tools/skill_ops.py` 中的 `SKILL_NAME_RE` 校验名称，不合法返回 `err("InvalidArgument", ...)`。

### T03 Heartbeat 主动通知真正送达用户

- **目标**：Heartbeat 产生的通知能真正到达用户（WebSocket 事件 + 空闲时语音），这是"主动交互"的最小闭环。
- **背景**：`core/heartbeat.py::_loop()` 调用 `await self.tick()` 后丢弃返回值，`get_queued_notifications()` 全仓库无人调用 → 主动通知从未送达。`core/server.py` 启动失败时 `logger.warning("Heartbeat start failed: %s", exc_info=True)` 格式串缺参数。
- **涉及文件**：`core/heartbeat.py`、`core/server.py`、`tests/test_heartbeat.py`。
- **实施步骤**：
  1. 测试先行：给 `Heartbeat` 传入 `on_notifications` 异步回调，调用一次循环体（把 `interval_sec` 设为 0 或直接测试新方法 `_run_once()`），断言回调收到 `tick()` 返回的通知；用户活跃时回调不被调用、通知进入队列；回调抛异常时循环不退出并写 `heartbeat_error.log`。
  2. `Heartbeat.__init__` 增加可选参数 `on_notifications: Callable[[list[dict]], Awaitable[None]] | None = None`。
  3. 抽出 `async def _run_once(self)`：`notifications = await self.tick()`；非空且有回调时 `await self.on_notifications(notifications)`；回调异常写错误日志。`_loop()` 改为 sleep 后调用 `_run_once()`。
  4. `core/server.py` 构造 Heartbeat 时传入 `on_notifications=self._deliver_proactive_notifications`；新增该方法：对每条通知 `await self.send_message("proactive", {"event": "heartbeat", "notification": n})`；若 `self.active_websocket` 存在、UI 状态为 `IDLE` 且非纯文本模式，再 `await self.mouth_speak(n["content"], "neutral")`（与后台任务完成通知的条件一致，参考 `_should_notify_background_completion`）。内容为空的通知跳过语音。
  5. 修正 `logger.warning("Heartbeat start failed", exc_info=True)`。
- **验收标准**：新测试通过；原有 `tests/test_heartbeat.py` 全部通过；服务端在 HEARTBEAT.md 有启用项时，空闲状态下能收到 `type: "proactive"` 的 WebSocket 消息。
- **测试命令**：`python -m pytest -q tests/test_heartbeat.py tests/test_server_helpers.py`，然后全量。
- **日志要点**：说明送达条件（何时只发事件、何时语音）。

### T04 前端显示主动消息 + 用户反馈回传

> 2026-10-14 拆分：后端部分（步骤 3：通知 `id`/`source`、`proactive_feedback` 消息处理、反馈持久化、accept 动作分发）已作为 T04 完成；前端部分（步骤 1、2：`main.ts` 气泡与按钮）改为 **T04b**，UI 是外壳，优先级低。T04b 只需按下面的消息协议发送反馈即可，后端已就绪：
> 发送 `{"type": "proactive_feedback", "id": <notification.id>, "action": "accept"|"snooze"|"mute"}`；收到的消息形如 `{"type": "proactive", "event": "heartbeat", "notification": {id, source, type, content, timestamp, action?}}`。

- **目标**：Live2D 前端能显示主动消息气泡，用户可点"好的 / 稍后 / 别再提醒"，反馈回传后端。
- **涉及文件**：`kage-avatar/src/main.ts`、`kage-avatar/src/style.css`、`core/server.py`（WebSocket 收消息处）、`core/heartbeat.py`（记录反馈）、新增测试 `tests/test_proactive_feedback.py`。
- **实施步骤**：
  1. `main.ts`：在 `data.type === "job"` 分支旁加 `data.type === "proactive"` 分支，派发 `window.dispatchEvent(new CustomEvent('kage:proactive', {detail: data}))`，并渲染一个可关闭的气泡（复用现有样式变量，3 个按钮）。
  2. 按钮点击通过同一 WebSocket 发送 `{"type": "proactive_feedback", "id": <通知id>, "action": "accept"|"snooze"|"mute"}`。
  3. 后端：T03 的通知字典增加稳定 `id`（`uuid4().hex[:12]`）和 `source`（如 `heartbeat:<检查项名>`）。在 WebSocket 消息分发处识别 `proactive_feedback`，调用 `heartbeat.record_feedback(id, action)`，追加写入 `~/.kage/proactive_feedback.jsonl`（字段：时间、id、source、action）。
  4. 测试：后端单元测试覆盖 `record_feedback` 写文件与非法 action 拒绝；前端用 `npm run build` 通过类型检查。
- **验收标准**：单元测试通过；`cd kage-avatar && npm run build` 无错误。
- **日志要点**：附消息协议（字段表）。
