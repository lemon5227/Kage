## 需要纠正的四个问题

### 1. 局部完成替代了目标推进

10月7日起、截止本次基线的49条提交中，43条标题命中 native/AX/lifecycle/TextEdit/activation/text/observer/scope；这是粗略主题计数，不能当工时或费用统计。过程 ledger 的 Task1–10 也集中于原生链与诊断。Task10 的审查认真检查了时间窗、scope、清理、预算和报告措辞，但没有把“本包是否推进成长闭环”设为前置验收。

因此，“每包有测试、审查、报告且通过”与“方向正确”是两件事。每次只限制一个探针不够：完成后不断派生下一个探针，整条支线仍会无限延长。

**修正：** 冻结 TextEdit dev5、新AX/OCR/跨应用适配和外壳扩展；恢复条件必须是下述成长任务确实需要它们。每轮支撑修复最多占一个包，第二个连续支撑包前必须说明为什么现有文件/代码环境不能继续核心实验，否则切回核心任务。禁止自动生成诊断子任务链。

### 2. 自修改的人工贡献没有成为主要验收维度

`scripts/experiments/recovery_evolution.py:73` 的 `failure_reason` 已由开发者写明“读代码后停止、未用已有技能、应修改recovery去选工具”。生成代码是真实的，但诊断与修改对象是人工提供的。候选还使用 repair/python/function/knapsack/selection 关键词和默认 `choose`；这是窄域恢复策略。不能把这轮实验扩大为自主发现瓶颈和通用自进化。

**修正：** 首轮允许开发者预先限定唯一可改对象（recovery），明确记作研究设计；实际失败识别、候选内容、验证及采用由运行中的管线完成。不能每次失败后由开发模型手写诊断答案、指定技能ID、修补候选，再归因于Agent成长。人工介入另记新版本与开发成本，不抹去旧失败。

### 3. test 参与最终激活，证据层级需要降格

`recovery_evolution.py:82–90` 先用dev比较，然后以新变体test通过作为根目录 `active.json` 的写入条件。没有证据表明生成器读取了test答案；但这个test实际上参与了最终选择，应视为额外验证门，而非完全独立的最终评测。旧报告关于生成前冻结仍成立，0→1也不因此作废。

**修正：** 后续采用开发数据生成、独立验证集晋级、最终评测集仅报告的划分。小预算也必须隔离用途，不必建复杂平台。先锁定晋级版本再跑最终评测；若根据评测结果改方法/撤销发布，将该批标记为已暴露并保留成绩，未来收益另用新集评估。旧E3新变体可作历史回归，不再称新盲测。

### 4. 最新“E2.1→E3.1→E4”仍是模块清单

完整谱系不是第一条闭环的必要条件；缺少两种已证明有效的改进对象时，比较路由算法没有意义。`Promoter` 已能在开发对照无收益/退化时拒绝晋级，但实验拒绝候选与已激活版本在后续任务退化时自动回退并非同一能力。

**修正：** E2仅补实际消费所缺的最小字段；先一个改进对象的闭环与持续采用，再第二失败机制，最后才评估是否需要E4。首次拒绝候选、重启加载、运行时禁用坏版本都要分开报告。

## 新执行顺序：先闭环，再扩展，再研究

以下是下一执行模型的任务规格，尚未实现或运行。G是本次验收门，不是新增子系统。当前只领取G1；后续有条件进入，不能以“代码包完成”自动跨门。

### G1：让已有窄域恢复能力成为持久的自动闭环

**目的：** 补齐失败触发→生成→验证→采用→下一任务使用的连接；复用文件/代码环境和既有技能，首轮只改recovery。此门证明集成与自动性，不将旧knapsack结果重新包装为新泛化成果。

1. 从 `search.py` 的有限循环、`RecoveryMutator`、`Promoter`、`KageChainProvider` 与已有候选状态复用，先提交一页实际调用图和最小缺口清单。不得再造runner、数据库、评分器或通用路由框架。
2. 任务入口连续接收文件/代码任务；真实外部失败被机器归类为能力失败或基础设施失败。能力失败可按预先固定规则进入唯一recovery改进通道；网络/权限/服务失败停止，不触发无意义演化。
3. 学习输入来自实际可见轨迹、公开目标及允许的验证反馈，保留来源；不使用针对本次任务手写的修复建议、隐藏评分答案或最终评测数据。限定recovery是本轮设计，不声称自动选择了修改对象。
4. 验证通过后保存active版本；后续任务及一次新进程重启从该状态加载，不再手工传新candidate路径/技能ID。记录来源episode、parent/child digest、验证结果和实际加载/调用digest即可，不先建完整多样性档案。
5. 退化候选保持父版本；坏digest/不兼容或运行时故障禁用该激活版本并回到最后已验证父版本，终止或有界重试须按协议，副作用不得无条件重放。受控故障注入只验工程机制，与真实模型生成结果分表。
6. 提交一条连续证据：失败→运行中生成源码→验证决策→重启→新输入任务真实采用→独立结果。执行框架与教师贡献分别记录。候选若无收益，保持失败结论，G1不能写“能力提升完成”。

**首包资源边界：** 最多2个候选，每候选首提案+最多2次格式修复（合计最多6次教师请求；语义失败不是格式修复）。开发/验证真实任务运行总上限12次，父子每次同为最多6本地请求、5循环步、150秒；缺失的硬预算能力必须在运行前说明。教师每次输出≤3000tokens、请求≤12000字节；先按当时配置填写明确费用上限，并纳入账本，无限额不得运行。这里仅制定规则，本轮未授权或启动额外付费实验。

固定全部任务、候选上限、请求/动作/时限和停止规则后运行；不为获得成功临时提高其中一臂预算。用尽限额、环境阻塞，或候选仅靠人工修补才可用，则输出失败归因，回到审查而非自动创建第三个候选/新诊断系列。聚焦测试验证接线；仅改文档不跑全量。

### G2：第二次改进与保留旧能力

G1闭环证据成立后，选择另一类现有文件/代码真实失败；不是只改文件名、函数名或数值。先证明原版本在该机制上有缺口，再决定需要生成新L1技能还是修改同一recovery；每轮只改变一层。保留上轮任务作回归，机器完成第二轮生成、选择和后续采用。

输出两次连续学习事件的来源、成本、版本及任务结果；用旧能力不退化和新能力改善验收。至少包含无相关技能/不适用技能的情形，不能把错误技能硬调用当成功。若第二机制没有真实失败或无收益，记录这个结果，不制造失败来支持故事。

### G3：冻结最终评测，验证机制是否值得保留

在开发与晋级验证完成后，对冻结的最终版本做父版本、演化版本、最简单固定策略三个对照。E3对照共享同一技能目录和提示，固定策略只用于判断生成recovery是否优于一个通用简单分派规则；L1实验则明确对照测量的是技能+发现策略整体。不得让控制臂暗含额外教师预算。

建议初始pilot固定12个新实例（至少3个任务族），三臂各一次，共36次；同任务预算，轮换执行顺序，全量报告。此数量是成本受控起点，不是统计显著性保证。测量完成率、误用/退化、实际模型请求和底层动作、耗时、一次性学习成本及后续累计成本；报告相同预算上限与实际消耗，不能混称严格同token。

最终评测不参与本轮候选选择，不按成绩追加样本。效果不足时缩小结论；若简单固定策略相当或更好，优先保留简单策略，不急于上FCER。只有两种以上改进通道各自有效且“选错对象”成为实际瓶颈，才领取E4。E6的预注册和记录从G1开始，研究结论等数据支持后再写。

## 给执行模型与审查模型的工作约束

每个工作包开始先回答：这包改变哪一种Agent行为？基线失败在哪里？结束后哪条新证据会改变我们对学习能力的判断？答不出则不进入实现。不得自动领取旧队列最近一个未勾选项。

每包汇报按：**新增行为 → 实际执行者与人工干预 → 原始分母/父子对照 → 重启后实际版本 → 学习与推理成本 → 未通过项与停止决定**。测试数量、提交数和文档篇幅放工程附注。

审查分两层：先审目标贡献和实验设计，再审代码正确性。正确实现低价值任务仍可判“此包不应继续”。复用现有工具和环境；不因看到新论文、框架或一个难解的GUI现象自动扩张范围。换模型必须作为显式独立变量，不把更强模型本身的能力记作系统学习。

**当前最小阅读集：** 根目录roadmap.md；实施时按需读取G1涉及源码、E3/C4对应原始失败。旧大篇交接与历史“next”仅在需要接口细节时读取。执行前检查两checkout的未提交文档，不能丢掉本次纠偏再从旧HEAD领取。

## 可对外声明的边界

目前可说：实现了受控环境中教师辅助技能生成、技能迁移、有限候选搜索及恢复模块源码生成/加载，有单任务家族小样本改善和完整负结果。

目前不可说：已具备持续自主成长、广泛跨任务泛化、日常主链自动进化、已验证线上回退、权重自学习，或浏览器技能稳定胜过原模型。当前没有完整成本审计，不能量化多少token“浪费”；可以确定近期大量工程投入没有带来相应成长证据。
