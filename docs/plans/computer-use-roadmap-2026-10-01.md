# 通用电脑执行详细路线（C0–C8）

原总规划§19，保留技术设计与研究来源。只在领取对应任务时阅读该包；实时状态见[总规划](../agent-memory-evolution-master-plan-2026-09-29.md)。

## 19. 通用电脑执行路线：吸收 Jev、SGLang 与 Rungic（2026-10-01）

### 19.1 目标、证据和当前资源

长期目标是通用电脑 Agent：能完成跨应用、多步任务，从失败与人类示范中积累可复用能力。起步任务集覆盖有限代表场景，不能把通过这些任务写成“人能做的 Kage 都能做”。本节是待实施规划，来源项目的结果与 Kage 自己的结果分开记录。

用户资源为 M4 Air 16GB、廉价云模型 API 与不保证型号/可用性的 Colab GPU。已实际运行 Qwen3-4B：现有 Kage 链在三类任务、各两次尝试上，llama.cpp 为 0/6，MLX 为 1/6；另一个同时改变停止策略、上下文和工具历史的 MLX 诊断循环为 3/3。它定位了脚手架问题，不能证明 MLX 提高智能或某个单独机制已经修好。详见 [真实推理报告](../runtime-engine-experiment-2026-09-30.md)。

当前采取以下约束：

- 不开始自行训练 Jev 类模型；E7 仍为可选支线，不领取训练任务、不申请训练 GPU。
- Jev API 后续可接入；当前主线不需要 Jev 凭据，也不自动产生相关费用。
- 保留现有本地 Qwen 与云端 provider；本轮不更换默认推理引擎。
- 观察和执行在本机完成；计划、文字生成与疑难恢复可交给云模型。
- 先以功能、任务成功和研究证据为优先，避免扩展成完整手机操作系统或独立桌面平台工程。

### 19.3 目标架构与最小契约

```text
用户目标 → 计划 / 当前子目标（本地或云模型）
                     ↓
观察器：浏览器 DOM / macOS Accessibility / OCR / 必要的视觉理解
                     ↓
当前状态摘要 + 当前可执行候选 + 最近动作与结果
                     ↓
可替换决策后端：现有生成模型 → 可选 Jev API / Qwen 分数后端
                     ↓
执行器：重新确认目标 → 执行动作 → 读取新状态
                     ↓
结果检查 → 继续 / 恢复 / 升级云端 / 请求人类示范 / 完成
                     ↓
轨迹与经验档案 → 可执行技能 → 留出任务复验 → 晋级
```

观察与执行接口按能力划分，优先 API/脚本、DOM、Accessibility；缺少结构信息时用 OCR 或视觉。这个顺序是效率策略，不排除绘图、canvas 等任务的视觉需求。OCR 框与真正可访问性控件需标注不同来源，不能把文字框误认成保证可点击的按钮。

新增接口由后续分包实现；以下字段是规划契约，不是当前已有 API：

```python
observation = {
    "observation_id": "o17", "surface_id": "browser:test-tab", "revision": "r9",
    "state": {"goal": "保存姓名", "remaining": ["填写姓名", "保存并读回"]},
    "candidates": [
        {"id": "c1", "operation": "fill", "target_ref": "e3",
         "description": "姓名输入框", "value_ref": "user.name"},
        {"id": "c2", "operation": "click", "target_ref": "e5",
         "description": "保存按钮"},
        {"id": "c3", "operation": "blocked", "target_ref": None,
         "description": "当前没有合适动作"},
    ],
}
decision = {
    "observation_id": "o17", "candidate_id": "c1",
    "backend": "existing_provider", "probabilities": None, "confidence": None,
}
# 只有确实提供分布的后端才记录 probabilities；不从自由文字虚构 confidence。
# executor.execute(observation, decision) 返回实际动作、outcome、后续 observation 和耗时。
# verifier.check(goal, fresh_observation, artifacts) 返回 passed / failed / unknown 和证据。
```

首版采用完整动作候选，避免操作与目标组合不兼容。后续确有延迟收益时，可借鉴 jev-ultrafast 的多问题方式同时预测 operation / click_target / fill_target；每个目标集合按操作过滤，最终只执行选中操作的目标。多问题一次网络请求不表示所有后端只做一次模型计算。

目标引用由观察器解析成 DOM 节点或 AX 控件，不让模型自行生成坐标或 selector 代替真实目标。执行前检查当前窗口/页面及目标是否仍有效；变化后重新观察和决策。用户给出的精确字段值直接绑定；确实需要自由文字时再调用 writer。

`DONE` 仅为停止建议。文件任务检查实际内容/行为；浏览器检查保存后的页面或后端记录；原生应用检查字段读回或实际产物。未知不冒充通过。云端升级应覆盖循环无进展、缺少可用候选和验证持续失败，不能只在 provider 网络报错时触发。

### 19.4 实施包与独立提交边界

本路线补足 E0/E1 的通用执行证据，再把经验交给 E2、把恢复改进交给 E3；不替换既有技能候选、外部评分和晋级机制。执行顺序为 C0 → C1 → C2；C3 为可选后端实验，C4 接入 E2/E3，C5 为后续体验探索。

### 19.6 LocateAnything-3B：截图目标定位（C6，P1，衔接 C1/C2）

用户此前给出的 NVIDIA 3B 来源是 [原帖](https://x.com/0x0SojalSec/status/2104717495055851883)，对应 [LocateAnything-3B 官方模型](https://huggingface.co/nvidia/LocateAnything-3B)、[论文](https://arxiv.org/abs/2605.27365) 和 [官方代码](https://github.com/NVlabs/Eagle/tree/main/Embodied)。官方 README 记载 ECCV 2026 接收，不按二手文章误记为 CVPR。它是视觉语言 grounding 模型，擅长根据描述定位目标，支持 GUI 元素、文本区域、物体和文档布局；不是完整任务规划器，也不是图形生成模型。

**采用职责：** 当 DOM/AX 无有效目标或界面只有图像时，输入截图与具体目标描述，例如“左侧工具栏的裁剪按钮”，输出框或点，再交给 C1 的执行器。当前决策模型或云规划器负责选动作，LocateAnything 负责找位置，执行器负责操作，C2 负责结果检查。Jev API 暂不接入也能独立验证这一能力。

**关键技术：** Parallel Box Decoding 一次预测完整几何单元，避免逐坐标 token 解码；hybrid 模式可在并行结果异常时退回自回归解码。官方 H100 上的 boxes/s、相对 Qwen3-VL 的倍数衡量定位吞吐，不能改写为 Mac 上整项任务快十倍。

**Apple silicon 候选：** [社区 MLX 转换](https://huggingface.co/mlx-community/LocateAnything-3B-4bit) 已提供约 2.96GB 权重。该名称的“4bit”实际为 mixed 4/8-bit，模型卡说明纯 4bit 会损伤坐标 token 精度；卡片还提示依赖专门 mlx-vlm 分支，不能直接认定当前正式版已支持。坐标为 0–1000 的归一化 token。实施前核对实际分支/修订、模型结构、processor 及 fast/hybrid 路径；通用 generate 跑通不代表 PBD 已被保留。

**实施与验收：**

- [ ] 独立实验环境先复现官方 `ground_gui(image, description, output_type="point")` 的定位结果；若使用 Colab T4，先检查 SDPA/FP16 路径，不能安装仅支持 Hopper/Blackwell 的 MagiAttention 后宣称 T4 可用。只做推理检查，不训练。

### 19.7 SoL-Pi：节约上下文并演化脚手架（C7，P1，衔接 E3/E4）

来源为用户给出的 [帖子](https://x.com/AYi_AInotes/status/2101465984284443129)、[NVIDIA 开源实现](https://github.com/NVlabs/SoL-Pi) 与 [2026-09 预印本](https://arxiv.org/abs/2609.20519)。官方实现是 Pi 扩展，不直接成为 Kage Python 依赖；吸收四项机制，保留 Kage 的 provider/实验内核。

| 机制 | Kage 实现方向 | 必须保留的证据 |
|---|---|---|
| Action Fusion | 有确定依赖的写入与校验在端侧连续完成，一次返回；仅在不需要新界面观察时融合动作 | 记录每项子动作、校验结果和耗时；校验失败回到恢复链，不能以融合为由跳过校验 |
| ObservationPack | 大输出原文落档，模型上下文只保留摘要和稳定引用，支持精确分页召回 | 同一引用返回同一内容；原始错误、路径及失败位置不被压缩掉 |
| Evidence-Preserving Reducer | 廉价模型提取诊断关键信息，引用逐条核对原始日志 | 引文与源内容匹配；失败保留原文；记录 reducer 额外调用及成本 |
| Online Context Compact | 已完成子任务后按上下文压力和成本收益压缩，保留当前目标、未完成步骤、证据引用与恢复信息 | 压缩后继续任务，不作为提前结束理由；待处理动作和工具结果不会丢失 |

实施时先检查 `core/prompt_builder.py` 的现有裁剪/历史逻辑、`core/agentic_loop.py` 的工具观察，以及 `core/evolution/artifacts.py` / runner 的归档机制，避免再造一个平行存储系统。

- [ ] 先做 ObservationPack：大日志/文件与重复观察各一个真实任务；测试分页召回与关键失败定位，再测 token 减少量。文件引用记录版本/摘要，不能随文件改写而指向新内容。
- [ ] 再做允许列表中的 Action Fusion，例如写测试文件后执行明确的检查；执行结果保留每一步，不将任意 GUI 点击批量化。
- [ ] Reducer 与上下文压缩逐项加入，分别独立提交；每项必须通过需要旧证据的长任务和中断恢复任务。小输出不因压缩多调用一次模型。
- [ ] 使用 C2 与代码任务的冻结留出集，比较无优化/单机制/组合：任务成功率、总输入输出 token、压缩或 reducer 开销、真实账单与任务耗时。保持模型、预算与任务一致。
- [ ] 把阈值、观察格式、可融合模式列为 E3 的可演化参数，先人工实现可复现基线；再由既有候选与晋级机制搜索，严禁修改隐藏 verifier 或删除失败记录来制造提升。

来源声称的节约倍数仅作为动机，不写入 Kage 预期验收目标；少 token 但少做了步骤或少验证结果，属于失败候选。

### 19.8 oMLX：通用本地服务与缓存验证（C8，P1）

筛选原则：只有直接服务现有任务、能在 M4 16GB 上测试、具有可用集成入口的方案才进入实施队列。模型专用的 Husky 从实施路线移除；不为它更换成 Woof，不再安排 Husky 试验。未经筛选的其他引擎也不自动加入任务。

[oMLX 官方仓库](https://github.com/jundot/omlx) 提供 Apple silicon 上的 MLX 服务，支持多类 LLM/VLM、OpenAI 兼容接口、工具调用、RAM/SSD 分层 KV 缓存，以及模型加载/卸载和内存控制。它比单模型专用引擎更适合 Kage 的本地文本推理、未来视觉模型与多轮 Agent 请求。它仍依赖具体模型架构、模板和后端支持，不等于任意模型都能运行；尤其不能据此认定 LocateAnything 的自定义 PBD 已受支持。

本包只验证 oMLX，已有 mlx-lm server 和 llama.cpp 保留为基线。oMLX 的优势假说是减少多轮重复 prefill、缓存恢复与模型切换开销，而不是默认假定单请求解码更快；单 worker 主线不以连续批处理的吞吐宣传作为采用依据。

- [ ] 用独立环境和端口启动 oMLX，复用现有 Qwen3-4B MLX 权重，不重复下载模型。记录实际版本、模型修订和模板；经现有 `OpenAICompatibleProvider` 对接，先验证工具 schema、参数、usage、多轮历史和停止行为。
- [ ] 使用相同 MLX 权重、任务、提示、采样与调用上限，对比 mlx-lm server 与 oMLX；llama.cpp 的不同量化结果单列，不算纯服务实现对照。C0 修复前后不能混进同一后端比较。
- [ ] 分别测冷缓存、同前缀连续请求、编辑中部历史后的部分前缀复用和服务重启后的 SSD 缓存恢复；记录命中/未命中与 prefill 时间，不能把冷/热状态混合成一个加速倍数。
- [ ] RAM 热缓存与 SSD 缓存均设明确上限；起步 SSD 上限 1GB，先检查当前可用磁盘，避免自动策略占用过多空间。系统至少预留 5GB 磁盘；不满足时关闭 SSD 缓存先验收服务，不清理用户文件腾空间。内存上限根据实际系统压力设置，不能将磁盘 KV 缓存解释为模型权重可超内存常驻。
- [ ] 文本服务通过后，再检查 C6 的视觉模型是否有真实兼容路径；不支持时保留独立定位进程，不以“支持 VLM”替代 LocateAnything 的 processor、坐标和 PBD 验收。16GB 上先按需顺序加载/卸载，不能默认多个模型同时常驻。
- [ ] 采用依据为任务完成率不下降，且重复请求/完整任务耗时或内存表现有可重复收益。所有结果含失败、冷启动和 SSD 占用；收益不明确则继续使用现有服务。
- [ ] 完成后停止测试服务；默认服务替换单独提交，保留切回旧 endpoint 的方式，不与 C0 修复捆绑。本节仅规划，未安装或实测 oMLX。

最终路线是：C0 修执行 → C1/C2 建立真实电脑任务 → C6 补视觉定位与 C7 降低脚手架开销 → C4 示范与技能成长；C3/Jev API 和 C8 引擎试验可按资源穿插，但不先启动 Jev 自训练。
