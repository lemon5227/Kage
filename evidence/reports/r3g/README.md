# R3g：训练数据保留“写后读回”（Kaggle v42–v44，2026-11-01）

**问题**：R3 训练后学生不再“写完读回检查”（原学生约一半题会读回，R3 为 0）。之前猜这是留出题塌掉的原因之一：原学生靠“写 → 读回 → 改”修好自己的第一版。只把读回步骤放回训练数据，能不能把留出题救回来？

**做法**（只改一处）：R3 的数据和超参数不变，在每条“最后一次 write_file → 最终回答”的轨迹中间精确插入一步 read_file 同一路径（工具返回内容是确定的，不需要重新采集；`scripts/experiments/r3_data.py --readback`，+273 行，1677/223 → 1920/253）。两个 seed（r3g0、r3g1），T4 fp16，480 步：v42 第一轮（g0 第 132 步被系统 SIGKILL，g1 停在 415 步），v43 从检查点续完（GGUF sha256 `cf2a8b86…` / `af764c78…`）。v44 评测，协议同 R3t（文件/网页每臂 3 次 + 1 次同会话原学生 A0 + 通用检查）。

```
python3 evidence/reports/r3g/analyze.py     # -> analysis.json（原始结果 evidence/kaggle/v44-results.tar.gz）
```

| | 学过·文件 | 留出·文件 | 学过·网页 | 读回率（写过文件的题） | 阴性误用 | 通用 |
|---|---|---|---|---|---|---|

| R3g seed 1 | **69/72** | 5/36 | 25/54 | **108/108** | 0/36 | 28/30 |

- **读回习惯完全恢复**：每一道写过文件的题都读回（原学生约一半，R3 为 0）。
- **学过的题不受影响**：两个 seed 61、69/72，对同会话原学生 +0.39、+0.50（p = 13/2048、3/8192）；与 R3 seed 1–2 合并比 +0.06（p = 13/32，无差别）。
- **留出题没有救回来**：两个 seed 都是 5/36。对同会话原学生 −0.44（7 降 1 升，p ≈ 0.07 / 0.05），对 R3 seed 1–2 +0.11（4 升 1 降，p = 3/16，不显著）。远低于修复判据 12/36。
- 误用 0/72，通用 28/30，与 R3 相同。

## 为什么读回了还是不行
逐题看留出题的轨迹（`analysis.json` 的 `held_out_repair`）：

| | 留出题 | 读回 | 读回后又改写 | 改写后通过 |
|---|---|---|---|---|
| R3g seed 0 | 36 | 36 | 0 | 0 |
| R3g seed 1 | 36 | 36 | 2 | 0 |
| 原学生 v44 | 12 | 7 | 0 | 0 |
| 原学生 v41 | 12 | 9 | 0 | 0 |

**原学生自己也几乎从不在读回后改写**：留出题上它通过的题，第一版就是对的。所以“写 → 读回 → 改”这条自我修复路径在这些评测里本来就不起作用；读回是一个检查姿态，不是修复手段。R3g 把这个姿态学回来了（而且比原学生更一致），但留出题的成败取决于第一次写出的代码质量，而 R3 训练损伤的正是这一点（R3e 分析里 `slugify` 的例子）。

## 结论
- **R3g 不是修复**：读回率 >0 满足了，学过题保住了，但留出题 5/36 < 12/36，RSI 第二轮的进入条件不满足。
- 修正了此前的一个推断（`r3e/analysis.md`、insights 里的“失去写 → 读回 → 改的自我修复路径”）：读回消失是训练数据形状的副产品，是真的；但它不是留出题塌掉的原因——原学生也不靠它修题。
- 剩下的方向是让回放覆盖被损伤的能力本身（写对没见过的代码）：R3f 自蒸馏代码回放。
